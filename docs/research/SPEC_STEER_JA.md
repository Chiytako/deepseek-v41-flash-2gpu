## 0. 結論 (可否・推奨手段・性能への影響・スコープ)

### 0.1 スコープ

本仕様は **中国語の出力混入の抑制** だけを扱う。モデルの拒否・安全挙動を変えること (無検閲化) は範囲外である。
中国語混入の主因は量子化であり、回復 (L0/L1) と配信マスクで解ける (§0.2)。

### 0.2 中国語混入の抑制: 可否と推奨手段

**可能。** 日本語性能を「原 1017 比で維持」したまま、混入率は原重みより下げられる。優先順位は次のとおり。

| 優先 | 手段 | 効き方 | 日本語への影響 | 根拠 |
|---|---|---|---|---|
| 1 | **量子化誤差の回復** (r3_qad L0 Viterbi+refit → L1 日本語/中国語 Hessian 校正) | 混入の**主因**を断つ。v0 は原重みの 8〜15 倍の確率を中国語トークンに置く | 日本語 KL も同時に下がる (同じ裾の回復) | r5_zh §3.2【実測】 |
| 2 | **配信時のスクリプトマスク** (回答部分で簡体字専用トークン Z1 を -inf) | 残った混入を**ほぼ 0** にする。中国語コーパスの簡体字を 98.9% 捕捉 | 日本語誤抑制ほぼ 0 (日本語 409 万トークンで 21 回、中国地名引用のみ) | r5_serve §1.1, §1.2【実測】 |
| 3 (任意) | **中間層限定の言語方向 steering** (biprojected, 日本語成分を抜く) | 字単位で拾えない「日本語漢字だけの中国語語」に効く可能性 | 端の層で触ると日本語劣化の危険。当てにしない | §2.3【実測+資料】 |

- 手段 1・2 は独立に掛け合わさる。1 で裾を下げ、2 で残りを刈る。
- **量子化が混入を増やす** のは実測済み: ja16 回答の自由文で、1,000 トークンあたりの簡体字専用トークン質量は教師 (1017 原重み) 0.0078 → v0 (EXL3 K2 無校正) 0.0855 (約 11 倍)、agent24 で 15 倍【実測、top-32 下限、r5_serve §1.2】。
- **原重みはほとんど中国語に流れない。** 回答の argmax が簡体字専用になった位置は、教師・v0 とも 9,935 位置で 0。混入は温度を上げた長い生成で、裾から引かれて起きる現象である【実測】。
- **マスクは品質を下げない。** 混入しかける位置では、ほぼ常に日本語の字体が top-1 にある (约→約 0.977、英语→英語 0.929、头→頭 0.939)。マスクは量子化で増えた 1 種類の誤りを取り除くだけで、モデルは次点 (同じ日本語の語) を選ぶ【実測、r5_serve §1.2】。

### 0.3 「性能向上」の正直な範囲

原 1017 を超える日本語能力は、教師に合わせる量子化・蒸留では**出ない** (r3 §0、r3_qad §0.4)。想定用途 (日本語の指示でコードを書くエージェント) での体感改善は 3 つに分解して測る。

| 体感 | 指標 | 由来 | 目標 |
|---|---|---|---|
| 途中で中国語が混じらない | 回答の Z1 率、`zh_detect` の novel 中国語率 | L0/L1 の回復 + 配信マスク | GLM 実出力 (1 字以上 0.47% / 3 字以上 0.10%) 以下。マスク後 Z1 ≈ 0 |
| 日本語の文体が崩れない | 文体の揺れ、応答言語一貫性 (r3 §3.6) | L1 の日本語校正 | 原重み比で維持 (悪化なし) |
| 混入抑制で日本語が劣化しない | JamC-QA / JCommonsenseQA / MMLU-ProX ja、JA-KL (G-JA3/4/10) | 中間層限定の慎重な設計 | 直交化/マスク前より悪化しない |

- 混入率↓は原重みを超えて「良く」できる (原重みにあった混入を消すから)。日本語の正答率・自然さは原重みが天井。

## 1. 全体の順序と理由

```
(0) 配信スクリプトマスク  … 重み非依存。いつでも付け外し。まず入れる (§2.1)
        │
(1) 原重み (bf16/FP8/FP4) を教師として用意
        │
(2) EXL3 を符号化・蒸留 (混入の主因 = 量子化裾の回復)      ← 本仕様の中核 (§2.2)
        ├─ L0: Viterbi + scale refit   (無校正 2bit の裾を回復)
        ├─ L1: 日本語+中国語を含む Hessian 校正 (活性方向を歪めない)
        └─ L2: 層単位の局所蒸留 (+ 任意で日本語区分の中国語質量への小さな罰)
        │
(3) (任意) 中間層限定の言語方向 steering       ← 効果小・要慎重 (§2.3)
        │
(4) 評価: 区分別 KL / top-1、混入率 (zh_detect / Z1 率)、日本語タスク (§4)
```

理由:

- **配信マスクを最初に置く** のは、重みを一切変えず、量子化・蒸留のどの版にも独立に付け外しできるからである。品質 A/B を先に取れる (§5 の E1)。
- **量子化回復を steering より前に、かつ主役に置く** のは、混入の主因が量子化だからである (§0.2)。平均 KL を下げる校正だけでは裾が残る可能性があるので、QAD の評価と損失に中国語質量を独立項として入れる (§2.2, §4.4)。
- **steering を最後に・任意にする** のは、言語方向の直交化は日本語の漢字語を壊す危険があり、かつ gate.bias に「中国語 expert だけ下げる」即使える構造が無いためである (§2.3)。混入の大半は手段 1・2 で消えるので、steering は残差への保険にとどめる。

## 2. 各手段の仕様

### 2.1 配信時のスクリプトマスク (最優先・低コスト・安全)

**方式 (決定)**: 回答部分 (思考 `</think>` の後) だけで、簡体字専用トークン (Z1、13,029 個) の logit を -inf にする硬いマスク。柔らかい bias と語単位の禁止 (T2) は採らない。根拠は r5_serve §5.1。

- **Z1 の定義**: GB2312 にあり EUC-JP / EUC-JIS-2004 / Shift_JIS-2004 のどれでも表せない CJK 字を 1 字以上含む完全な UTF-8 トークン。`work/zh/serve/z1_ids.json` (13,029 個)、ds41rt 形式の許可マスク `work/zh/serve/allow_mask_z1.u32` (16,160 バイト、bit1 が許可)。
- **位相の状態機械** (要求ごと、ホスト側):

  | 位相 | 入る条件 | マスク |
  |---|---|---|
  | Think | prompt 末尾が `<think>` | 無し (思考は中国語を含みうる。質量は回答の 40 倍) |
  | Free | prompt 末尾が `</think>`(128822)、または Think 中に 128822 を出す | **Z1 禁止** |
  | Fence | Free 中にコードフェンスを奇数個含むトークン | 文脈の Z1 が 20 個未満なら禁止、20 個以上なら解除 |
  | Tool | Free/Fence 中に `｜DSML｜`(128825) を出す | 解除 (ファイル内容や引数に中国語が要ることがある) |

- **有効化の判定 (`auto`)**: 最新のユーザー発話 (最後の `<｜User｜>` から `<｜Assistant｜>` まで) だけで判定する。文脈全体で判定すると 5.3% の要求で抑制が外れる (過去の assistant 出力の混入が文脈に残るため、r5_serve §1.3)。発話に Z1 が 3 個以上 / 仮名なし CJK 20% 以上 / 中国語を求める語 (中国語・中文・簡体・繁体・拼音・Chinese・Mandarin・zh-CN 等) があれば off。それ以外は on。
- **ds41rt 実装 (段階 1, CUDA 変更なし)**: `logit_bias`/`bad_words`/logits processor は無い (送っても黙って無視、`tests/upstream_sampler.rs:7-9`)。ただし XGrammar 用の要求ごと語彙ビットマスク経路 (受付 anchor → ドラフト切り詰め → 検証マスク → GPU/CPU サンプラー → 接頭辞キャッシュ) が一貫してある。言語マスクを `constraints::State` に「静的拒否マスク + 位相」として合成し、文法マスクと AND を取る。Rust 約 400 行、`lang_guard.rs` 新規 + `constraints.rs`/`scheduler.rs`/`native_v41.rs`/`cli.rs` の改修。まず `shadow` モード (マスクせず Free で Z1 を出した回数を `/v1/stats` に記録) で実混入率を測る。詳細の行割りは r5_serve §3.3。
- **DSpark (投機デコード) との整合**: 目標側のマスクを正とし、提案を同じ状態機械で切り詰める。sample-and-match なので受理率は変わらない (切り詰めは検証の無駄を省くだけ)。ドラフト側マスクは不要 (argmax が Z1 の位置は 0)。r5_serve §3.4。
- **vLLM (A/B 用)**: `logit_bias`/自作 processor は投機デコードと併用不可。使える経路は reasoning-aware な structured outputs (xgrammar の文字クラス文法、`enable_in_reasoning=False`)。proxy が `auto` 条件の要求に EBNF `root ::= T ("<｜DSML｜" A)?` / `T ::= [^<簡体字1,007区間>]*` を付ける。r5_serve §4。
- **コード変更なしで今すぐ**: ツール無しの要求なら `response_format: {"type":"regex","regex": <answer_regex.txt>}` (`tools/zh_regex.py` が生成、2,278 字を 1,007 区間に) で回答の簡体字を禁じられる。品質 A/B を先に取るのに使う (§5 E1)。
- **性能への影響**: c1 では無視できる。c16 で段階 1 のホスト側コピーが約 0.5〜1.5%。超えるなら段階 2 (GPU 常駐マスク + 行フラグ、CUDA 30 行) で 0 に近づける。r5_serve §6。
- **誤抑制の扱い**: 中国の人名/地名は日本の字体に寄る (慣例どおり)。中国語学習/翻訳依頼は `auto` で off。稀な簡体字 (バイト片 1,072 字、出現の約 1%) は漏れるが、気になれば文字単位 regex か段階 1 の拡張 (約 60 行)。T2 (日本語漢字だけで書ける中国語語トークン、4,099 個) は GLM 日本語回答の 2.2% で**正当に**使われる (配列入力・不均一・不等式) ので禁止しない。r5_serve §5.2。

### 2.2 量子化誤差の回復 (混入の主役)

- **L0 (Viterbi + scale refit)**: 無校正 EXL3 2bit (v0) が持ち上げた裾を回復する。混入増加の大半はここで戻る見込み【推測、§0.2 の 11〜15 倍を回復対象とする】。
- **L1 (日本語+中国語を含む Hessian 校正)**: r3 §7 の構成 (日本語 40%、コード/エージェント 45%、英語 8%、中国語ほか 5%、画像 2%) を踏襲。中国語 5% の意味を 2 つにする: (i) 狭い校正で活性範囲が狭まる失敗を避ける、(ii) **V4.1 が中国語へ切り替わる経路の量子化誤差も校正対象に入れる** → その経路の誤差が減れば裾からの混入も減る。
- **L2 (層単位の局所蒸留)**: suh/svh と shared を教師に合わせる。**任意で、日本語区分で簡体字専用トークンに置く質量への小さな罰 (または逆向き KL 項) を小さい係数で足す。** v0 の中国語質量は平均 KL とほとんど相関しない (順位相関 0.04、上位 1% の位置が増加分の 54〜63% を持つ) ので、前向き KL だけでは裾を見落とす。ただし教師 (原重み) 自体の混入が少ないので、過剰な罰は日本語漢字語を歪める。α は小さく、G-JA10 で監視する。r5_zh §4.4。
- **評価への反映**: v1/QAD 版を作るたびに、区分別 KL と並べて Z1 質量 (`tools/zh_teacher_mass.py`) を独立の関門として記録する (§4.4)。

### 2.3 (任意) 中間層限定の言語方向 steering

**位置づけ: 最後の手段・効果小・要慎重。** 手段 1・2 で混入の大半が消えるので、字単位で拾えない「日本語漢字だけで書ける中国語語」(可以・支付 等、共有 kanji の 15,571/21,362 トークン) への保険にとどめる。

- **方向の作り方**: `harness/steer_collect.py` (CPU self-test 済み) で日本語系列と中国語系列を別々に collect し、層ごとに MoE 入力/残差の平均差。対訳 (FLORES-200) で内容差を相殺 (ReCoVeR に倣う)。**中国語系列の routing・残差は未取得** (§6.2)。
- **直交化を焼くときの注意【実測、`tools/zh_ortho_fp8.py`】**: FP8 に naive に戻すと方向の約 40% が復活する。列ごとに丸めを一部反転させる requant で 0.1% まで除去でき、再構成誤差はほぼ増えない (naive 1.02% vs 補正 1.21%)。EXL3 の routed `w2` (2bit trellis) は符号化後に方向を打ち消せないので、**符号化前に直交化した重みを符号化する** 必要がある。
- **日本語を壊さない 3 対策**: (i) biprojected / norm-preserving (grimjim) — 中国語方向から日本語成分を射影で抜いてから除去し列ノルムを保つ、(ii) 方向と共有 kanji 部分空間の cos を測り高ければ α を下げる、(iii) 区分別 KL と対照ゲート (G-JA3/G-JA10) で直交化前より悪化しないことを確認。
- **gate.bias は使えない**: bias は層ごとにほぼ一定の大きな値 (平均 +9.8〜+32.7) で、平均からのズレの std が 0.02〜0.15 しかない。日本語特化 expert の bias 平均は層平均とほぼ同じ (15.79 vs 15.80)。「中国語 expert だけ bias で下げる」即使える構造は無い。SteerMoE 方式 (中国語で過剰活性・日本語で稀な expert を検出し中間層限定で bias を微調整) は正統だが、中国語 routing の取得が前提で、効果も小さい見込み。
- **層の選択**: Bandarkar+ に従い、言語特化が強い早い層 (0〜3) と遅い層 (36〜39) では routing/方向を触らず、中間層中心にする。端の層は日本語も担う。

## 4. 評価と合格基準

### 4.1 主指標 (混入率)

- **G-JA6** (r3 §2.3): 日本語回答の簡体字混入が 1 字以上 1.0% 以下、3 字以上 0.3% 以下。
- 生成評価: `zh_gen_eval.py score` の「混入計」= level 2 以上の割合 + 中国語で答えた回答の割合。
- v0 を推奨設定 (T=1.0) で使うと 3.5〜4.5% で **G-JA6 を満たさない見込み**【計算、r5_serve §1.2】。目標: L0/L1 回復 + マスクで 0.1% 以下。

### 4.2 日本語品質 (混入抑制で劣化していないこと)

- judge 点 (ELYZA / MT-Bench ja)、正答率 (MGSM ja / JamC-QA / JCommonsenseQA / MMLU-ProX ja)、規則順守 (M-IFEval-Ja)。
- 区分別 KL と top-1 一致 (`results/QUALITY.md` の指標)。JA-KL が校正/マスク前より悪化しないこと (G-JA3/4/10)。
- ツール呼び出しの評価 (155/176 前後) が変わらないこと。

### 4.3 連続指標 (件数が少ない比較用)

- 回答の on-policy の zh_only / Z1 質量 (1,000 トークンあたり)、回答 1 本あたり 1 回以上引く確率。
- teacher-forced 指標 (E2/E3): 回答自由文の質量、字体双子の質量を教師比で。

### 4.4 QAD への関門

- v1/QAD 版の teacher-forced で、回答自由文の Z1 質量が教師の 2 倍以内。KL とは**別の**関門にする (平均 KL では裾を見落とす、§2.2)。
- マスクの KL への寄与は 1 トークンあたり約 1e-4 nats で、v0 の ja KL 0.206 に対し誤差の範囲。混入率 (G-JA6) にだけ現れる。

## 5. 実験計画 (GPU が空いてから。最初の 3 つ)

いずれも中国語抑制のための実験で、安く・最初に立てられる。GPU と稼働サーバが要るものは「v1 量子化が空いてから」。コンテナには触れない。

### E1 配信マスクの品質 A/B (最優先・コード変更なし)

- **目的**: マスクが日本語品質を落とさず G-JA6 を改善することを、重みを変えずに確認する。これが取れれば、段階 1 の daemon 実装 (Rust 400 行) に進む判断ができる。
- **方法**: v0 の ds41rt に、ツール無し日本語評価 (ELYZA-tasks-100 / Japanese MT-Bench / MGSM ja / M-IFEval-Ja) を temperature 1.0 で、`response_format` regex (`tools/zh_regex.py` の `work/zh/serve/answer_regex.txt`) の有無で A/B。
- **見る値**: G-JA6 (混入率)、judge 点、正答率、規則順守、DSpark 受理率 (`/v1/stats`)、1 回目の文法コンパイル時間。
- **合格**: G-JA6 が 3〜4% → 0 近く、他の指標は誤差の範囲。
- **コスト**: ツール無し約 70 本 × 2 条件。GPU 空き後すぐ、数時間。コンテナ改修なし (既存 API)。

### E2 層の二分探索 (量子化の混入増加がどこか)

- **目的**: v0 の中国語質量増加がどの層群に起きるかを特定し、L1 校正の重点層を決める。言語特化は端の層に寄る (r3 §1.1) という予想を検証。
- **方法**: `harness/steer_zhbisect.py` で、v0 の EXL3 experts を層 0〜9 / 10〜19 / 20〜29 / 30〜39 のどれか 1 群だけに使い、ja16 を teacher-forced 採点。`tools/zh_teacher_mass.py` で中国語質量と字体双子の質量を出す。大きい群を 5 層ずつに割る。
- **見る値**: 群ごとの Z1 質量・双子質量 (教師比)。
- **合格判定ではなく切り分け**: 増加が中間層中心なら L1 の校正データ配分を中間層に厚く、端の層中心なら L0 の scale refit を端で強める。
- **コスト**: 1 回 15〜25 分、最初の 4 回で約 1.5 時間。harness (LIL イメージ内)。

### E3 温度の掃引 (サンプリング設定の寄与)

- **目的**: teacher-forced の予測 (回答 1 本あたり T=1 で 4% → T=0.6+top_p0.95 で 0.4%) が実生成でも成り立つか。推奨サンプリング既定値の判断材料。
- **方法**: ds41rt で v0 (と可能なら v1) を (T, top_p) = (1.0, 1.0)、(0.6, 0.95) の 2 点で生成 (`tools/zh_gen_eval.py gen`、200 本 × 2 seed)。`zh_detect.py` で採点。
- **見る値**: 混入計 (G-JA6)、日本語の多様性・推論の質 (温度を下げた副作用)、思考の主言語と回答混入の同時分布。
- **合格判定ではなく設計入力**: 温度で約 10 分の 1 になるなら、既定を下げるか、マスク (E1) と併用して低温に依存しない構成にするかを決める。
- **コスト**: 1 版 1 設定 1 seed で約 25 分、2 seed × 2 設定で約 2 時間。

> 以降の実験 (E4 expert 特定、E5 思考の言語、E6 文脈の対比較、E7 DSpark 有無、E8 Engram、生成本番) は r5_zh §4.2・§5 に設計済み。本仕様の中核 (手段 1・2) の判断には E1〜E3 で足りる。

## 7. 反証レビュー (2026-10-18、独立検証)

扱った範囲: 中国語混入の抑制に関わる配信側の実装可否 (ds41rt / vLLM のコードで照合)、評価と判定器の妥当性、文書間の矛盾。GPU 不使用、CPU で語彙・コーパス・判定器を再計算した。
扱わなかった範囲: mHC (hc_pre/hc_post/comb) を通した方向直交化の数式と、EXL3 routed `w2` の再量子化コスト。どちらも §2.3 (任意) にだけ関わり、手段 1・2 を採るかどうかの判断には影響しない。

### 7.1 【重大】Z1 マスクの捕捉率 98.9% は自分の定義で自分を測った値で、判定器の基準では 87% にとどまる

- 98.9% (r5_serve §1.1) は、分母の「簡体字専用字を含むトークン」を Z1 と同じ字の定義 (EUC-JP / EUC-JIS-2004 / Shift_JIS-2004 で表せない字) で数えている。このため、漏れとして残るのはバイト片だけになる。
- 一方、Z1 は JIS X 0212/0213 にある簡体字を日本語の字として扱い、許可している。この集合には、会話でよく使う中国語の字がまとまって含まれる。`zh_detect.py` の ZS (= `zh_only`) はこれらを中国語として数えるので、マスクの基準と評価の基準が食い違う。
- 【実測】`zh_only` (14,996 個) のうち 1,977 個は Z1 に入っていない。例は 你・么・没・个・关・两・运・达・种・吧・呢・啊・您・哪・帮・什么・怎么・没有・开始・影响・关系・关于・相关・你的 である。
- 【実測】中国語コーパスに出る `zh_only` トークンのうち Z1 が禁じる割合は、alpaca_zh_a で 2,800/3,210 = 87.2%、wiki_zh_1000 で 49,451/56,580 = 87.4% だった。V4.1 のトークナイザで数え、データは `work/zh/data/` を使った。
- 【実測】例文「你可以把这个函数改成异步的，然后运行测试看看有没有问题。」は 14 トークンで、Z1 が止めるのは 3 トークン (这个 など) だけである。`answer_regex.txt` も同じ字の定義なので、「什么」はそのまま通る (Python `re` で確認)。漏れるのは口語・疑問・二人称の字に偏っている。これはアシスタントの回答で混入しやすい語域そのものである。
- 修正案: マスクを `zh_only` 全体 (Z1 に 1,977 個を足す) に広げる案を E1 の第 3 条件として加える。`corpus_rates` を見ると、現代日本語コーパス (oasst2_ja、dolly_ja、jsquad、mmluprox_ja、elyza100、jmtbench、mifeval_ja、research_md) での `zh_only` の出現は 0/M である。出現したのは wiki_ja (40/M) と aozora (27/M) だけで、旧字や異体字の引用と見られる【推測】。ただし、これまでの誤抑制の実測 (30,526 要求中 84 件) は Z1 についての値である。広げる前に、同じ集計を `zh_only` で GLM 実トラフィックの日本語回答に掛け直す必要がある。
- §0.2 と §2.1 の「98.9% 捕捉」は、「Z1 定義の字について 98.9%、判定器の定義では約 87%」と書き直す。

### 7.2 【重大】「マスク後 Z1 ≈ 0」は構成上必ず成り立つので、評価になっていない

- §0.3 の目標「マスク後 Z1 ≈ 0」は、マスクの定義からそのまま従う。7.1 の漏れ (什么・没有・你 など) を測れない。
- 主指標は、`zh_detect` の novel な level ≥ 2 (ZS は JIS X 0212/0213 の簡体字を含む) と、level 3 (中国語の句) に固定する。Z1 率はマスクが効いていることの確認にだけ使う。G-JA6 もこの判定器で測ることを明記する。
- マスクで Z1 を禁じると、モデルが漏れる側のトークン (什么・没有 など) で中国語の文を続ける可能性がある【推測】。E1 では level 3 (文単位) の件数を、マスクの有無で必ず比べる。

### 7.3 【中】判定器はコードを除いて判定するため、生成コードの中の中国語を測れない

- `clean()` は、判定の前にコードフェンスとインラインコードを取り除く (`zh_detect.py:190-200`)。
- 【実測】回答「このコードを修正しました。```python # 读取配置文件，如果没有就创建 ...```以上です。」は level 0 になる。
- コーディングエージェントの用途では、生成コードのコメントや文字列が混入の主な出先になりうる。そのうえ、§2.1 の Fence 位相 (文脈の Z1 が 20 個未満なら禁止) の効果を、今の評価では測れない。
- 修正案: `zh_gen_eval.py score` に、`strip_code=False` で、コードの部分だけを copied 判定込みで数える `code_zh` を別列として足す。§4.1 の指標にも加える。

### 7.4 【中】copied (文脈からの写し) を字単位で判定しているため、中国語を含む文脈で見落としが出る

- `split_novel` は、1 字の項目を「文脈に出た字の集合」と照らすだけである (`zh_detect.py:272-274`)。文脈に一度でも出た字は、回答に何回新しく出ても数えない。
- 【実測】文脈に「你」「没」があると、回答「你说的没问题。」の ZS は「说问题」だけになる (この例は句の規則で level 3 になるので、検出は落ちない)。
- 文脈に中国語がある要求 (1,605 件) は、§1.1 によれば混入が偏る区間である。そこで level 2 が過小に出る。これは偽陽性ではなく偽陰性の向きなので、混入率を楽観側に誤らせる。
- 修正案: copied 判定を、2〜3 字の n-gram が文脈に出たかどうか、または字ごとの出現回数の比較にする。

### 7.5 偽陽性について (概ね妥当)

- 現代日本語コーパスでの偽陽性 0 と、GLM 実トラフィックの level 2 の例がすべて本物の混入だったこと (r5_zh §1.4、§2.2) は、`corpus_rates` の値と矛盾しない。
- 残る偽陽性の源は、日本語の回答が中国の製品名・地名・人名を簡体字のまま正当に引く場合である (例: 飞书)。今の判定器はこれを混入として数える【推測、未計測】。コーディングエージェントでは中国系のライブラリや企業名で起こりうるので、E1 の bad 例では「固有名詞の引用」を別ラベルにして目視で確かめる。

### 7.6 【中】vLLM 経路の記述が文書間で食い違っている

- §6.2-1 の「まず vLLM-exl3 (r4) の `allowed_token_ids` で効果・誤抑制を測る」は、r5_serve §4 と §2.1 に反する。r5_serve §4 には次の根拠がある。
  - `logit_bias` は、投機デコードと併用すると要求時にエラーになる (`sampling_params.py:1038-1050`)。
  - 自作の logits processor は、投機デコードと併用すると起動時にエラーになる (`v1/sample/logits_processor/__init__.py:42-46`)。
  - `allowed_token_ids` は思考の部分にも効き、要求ごとに約 0.7 MB の JSON を送る必要がある (`rejection_sampler.py:328-346`)。
- 修正案: §6.2-1 を「vLLM では structured outputs (xgrammar、`enable_in_reasoning=False`) で測る」に直す。

### 7.7 確認済み (正しい)

- ds41rt に `logit_bias`/`bad_words` の面が無いこと: `rust/crates/ds41rt-api/src/tests/upstream_sampler.rs:8-9` の注記どおり。
- E1 の regex は回答部分にだけ効く。根拠は次の 2 点で、§2.1 と E1 の前提は成り立つ。
  - `native_v41.rs:238-241` が、regex の `response_format` を text として描画し、元の指定を強制用に保持する。
  - `native_v41/constraints.rs:26-28, 45-50` は、thinking のとき `sequence[any_tokens(exclude 128822), token 128822, regex]` を組み立てる。
- ツールがあるときは `or[answer, calls]` になる (`constraints.rs:33-37`)。回答の文とツール呼び出しを混ぜられなくなるので、E1 を「ツール無しの要求に限る」としたのは正しい。
- 文法の経路は字の水準でマスクするので、バイト片の漏れ (§2.1) は regex の対象の字については閉じる【推測、XGrammar の文字クラスはコードポイント単位】。ただし対象の字の集合は 7.1 の漏れを含んだままである。
