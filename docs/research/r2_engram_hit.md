# X2: Engram 行ヒット率の実トラフィック測定 (CPU のみ)

作成日: 2026-10-18 / 対象: `deepseek-ai/DeepSeek-V4.1-Flash-1017` の Engram 表 (層 1 と 14、各 3.84 億行、1 行 256B + scale 8B)
入力: GLM-5.3-Flash の要求ログ (173 ファイル、19GB。コーディングエージェント型の実トラフィック、複数のクライアント)
スクリプト: `tools/x2_*.py`。中間データは `work/x2/`。全数値の出典は `work/x2/report_full.txt` (`x2_report.py` の出力)。
凡例: 【実測】はこのシミュレーションの値。【計算】は実測値からの式。【推測】は根拠が間接的な値。GPU は使っていない。glm53v コンテナには触れていない。

---

## 0. 結論

1. **行単位の LRU キャッシュ 32GB で十分である。** 後半の実トラフィックで、Engram アクセス (8k チャンク内で重複を除いた後) のヒット率は prefill 98.2%、decode 87.6%、全体 92.9% だった【実測】。
   - 48GB と 64GB は 32GB より 0.9 ポイントしか上がらない。PLAN の 60GB は過大である。
   - PLAN §4 X2 の判定基準は「64GB でヒット 55% 以上なら D3 を採る」だった。結果はこれを大きく上回る。よって **D3 (NVMe + RAM 行キャッシュ) を採る。D4 (MXFP4 化) は要らない。**
2. **方式は LRU にする。頻度順の固定表は LRU に負ける。**
   - 前半の頻度で選んだ静的表は、64GB でも 81.2% にとどまった (LRU 32GB は 92.9%)。
   - 理由は、エージェントのセッション内で同じ内容が繰り返し現れることにある (直前に書いたコードを読み直す、テスト出力を再度読む、など)。これは時間的な局所性であり、全体の頻度では捉えられない。
   - PLAN §2.4 D3 の「頻度順の固定 + LFU」は、**LRU (実装は CLOCK 近似) を主にし、必要なら頻度上位を pin する**形に改める。
3. **NVMe の IO は 1 トークンあたり prefill 0.58、decode 5.97 になる** (LRU 32GB、並べ直した表なら 1 行 1 IO)【実測】。
   - キャッシュが無い場合は prefill 31.2、decode 48.0 である。
   - prefill: 230k IOPS で割ると上限は約 40 万 tok/s になる。NVMe はもう律速しない。キャッシュ無しだと 7.4k tok/s で頭打ちになり、PLAN の 6.7k と合う。
   - decode c16: 1 step (64 トークンを検証) あたり **382 IO** になる。c16 で 600 tok/s、τ=2.8 なら 13.4 step/s なので、約 5.1k IO/s【計算】。
4. **ページキャッシュも PLAN が見積もったほど悪くはない。それでも行キャッシュの方が約 4 倍、メモリ効率が良い。**
   - 4KiB ページの LRU を 64GB 持つと、IO は prefill 1.11 / decode 7.25 IO/token になる。これは行 LRU 16GB (0.87 / 7.68) とほぼ同じである。
   - PLAN の「容量効率 1/15、ヒット 35%」は外れていた。64GB は表 196GB の 1/3 を占めるためである。
5. **TP rank の間で IO が偏る。** 公式の分割 (rank ごとに先頭から ceil(N/2) 行) では、miss IO の約 75% が rank 1 に集まる。
   - rank 1 には 3-gram の後半 4 head と 4-gram の全 8 head が載る。rank 0 には 2-gram の全 8 head と 3-gram の前半 4 head が載る。
   - lookup の数は 12 対 12 で同じだが、ヒット率が違う。
6. **日本語はコードより IO が多い。** prefill の IO/token は日本語 1.80、コード 0.59、その他 0.34 だった (LRU 32GB)。日本語は 8k チャンク内で重複しにくく (unique 0.79、コードは 0.65)、ヒット率も低い。decode では日本語 6.9、コード 4.5、その他 7.2 である。

## 1. 方法

### 1.1 要求の取り出し (`x2_extract.py`)

- ログは SGLang の request logger の形式である。1 行が 1 イベントになっている。
- `request.received.openai` には messages と tools が入っている。直後の `request.received` (rid と GLM でレンダリングした text) と、ファイル内の FIFO 順で対応付けた。対応は、最後のメッセージの先頭 40 文字が text に含まれるかで確かめた。
- 出力は `request.finished` の `out.text` から取った。これは GLM の生出力で、`…</think>本文<tool_call>名前<arg_key>…` の形をしている。これを reasoning、content、tool_calls に分けた。
- 対応が取れた要求は、OpenAI 要求 31,914 件のうち **30,526 件**だった【実測、`work/x2/req/_extract_stats.json`】。
  - 対応が取れなかったもの 925 件、完了イベントが無いもの 463 件、レンダリングの失敗 0 件。
  - `input_ids` だけを持つ合成ベンチ要求 (乱数トークン) は OpenAI イベントを持たないので、最初から含まれない。
- レンダリングには公式の `encoding/encoding.py` の `encode_messages` を使った。
  - モードは thinking (`enable_thinking` が False でない限り) で、reasoning_effort は "high" (75)。tools は system メッセージに付けた。
  - 出力トークンは、`encode(messages + [assistant])` から `encode(messages)` を除いた接尾部とした。こうすると次のターンの接頭辞と一致し、prefix cache が正しく効く。接頭辞が一致しなかった件数は 0 件だった。
- トークン化には V4.1 の `tokenizer.json` を使った。V4.1 のトークン数は GLM 比で 1.108 倍だった (新規 prefill の比)。

### 1.2 prefix cache と Engram の対象区間 (`x2_prep.py`)

- 30,526 件を到着時刻順に並べ、全体で共有する上限なしの prefix cache を通した。
  - 粒度は 256 トークンのブロックで、チェーンハッシュを使う。GLM の `--block-size 256` に合わせた。
  - プロンプトと出力の全ブロックを登録する。後の要求は、登録済みのブロックが連続する限り再利用する。
- Engram を引く区間は、要求ごとに「prefix cache に当たらなかったプロンプト部分」と「出力の全トークン」とした。
- 結果【実測、`work/x2/prep/prep_stats.json`】
  - プロンプト 5.82 億トークンのうち 92.8% が prefix cache に当たった。新規 prefill は 4,213 万、出力は 1,770 万で、Engram の対象は計 5,983 万トークンになった。
  - GLM 自身が報告した新規 prefill は 3,800 万 (cached 比 92.9%) である。V4.1 のトークン化での値 4,213 万と、トークン比 1.108 の範囲で整合する。
- テキストの分類は 256 トークンの窓ごとに行い、特殊トークンを除いて判定した。
  - CJK と仮名が非空白文字の 25% 以上なら **ja**。
  - ASCII のコード記号が 6% 以上なら **code**。
  - それ以外は **other** (英語の推論文、ツール JSON など)。
  - 対象区間に占める割合は ja 11%、code 49%、other 40% だった。

### 1.3 ハッシュ (公式との一致)

- `x2_sim.py` の numba 版ハッシュを、第 1 ラウンドの `engram_sim.py` (`ref/engram.py` の転記) と突き合わせた。
  - 内容: 圧縮語彙、素数、乗数、XOR のローリング、オフセット、系列先頭の pad、画像トークンを DEAD として扱う処理。
- 確認したこと
  - 圧縮語彙が **99092** で、`config.json` の `engram_compressed_vocab_size` と一致した。
  - 素数の総和で決まる行数が 384,006,168 / 384,016,682 で、`engram_num_embeddings` と一致した。
  - 実要求 3 件 × 2 パーティションで、行 ID の集合が完全に一致した (`x2_check_hash.py` の出力 `match True` ×6)。
- 画像トークン (`<｜deepseek_image｜>`、27 個) では lookup しない。n-gram もその位置で切る (ref の `token_mask` と同じ扱い)。

### 1.4 シミュレーション (`x2_sim.py`)

- **グループ**
  - prefill は新規区間の先頭から 8,192 トークンずつのチャンクに切る。
  - decode は 1 本の 4 トークンを 1 グループとする (DSpark の 1 検証 step)。
  - グループの中では同じ行を 1 回だけ読む。これを「重複除去後アクセス」と呼ぶ。
- **前半と後半**: Engram の対象トークン数で半分に切った。前半は 12,771 件、後半は 17,755 件。キャッシュは前半で温め、ヒット率は後半だけで数えた。
- **方式**
  - row static: 前半の重複除去後アクセス数の上位 K 行を固定で持つ。
  - row oracle: 後半自身の頻度で上位 K 行を選ぶ。静的表の上限にあたる。
  - row lru: 両 rank で共有する LRU。スタック距離から正確に計算した。
  - lru_rk / static_rk: rank ごとに K/2 ずつ分けた LRU と静的表。
  - page4K static / lru: 元の safetensors 配置 (行 r は `664 + 256r`、層 14 は 672) の 4KiB ページを単位にする。境界をまたぐ行は 2 ページに触れる。scale テンソル (6.1GB) は常駐と仮定した。
- **容量**: 1 / 4 / 16 / 32 / 48 / 64GB。行キャッシュは 1 行 264B、ページキャッシュは 1 ページ 4,096B で換算した。
- **並列化と RAM**
  - ページ番号を 64 で割った余りで表を 64 個に分け、1 プロセスが 1 個を受け持つ。
  - 64 個すべてを計算したので、**行のサンプリングはしていない** (sample_frac 1.000)。
  - 確認のため 1/64 だけで回した結果 (`work/x2/sim_test.json`) とも比べた。全数との差は主要な値で 0.3 ポイント以内だった (SHARDS 方式の空間サンプリングが成り立つことの確認)。
  - 6 プロセス並列で 7 分 51 秒かかった。RSS の合計は最大 26GB だった。このうち約 2.4GB×6 は共有している mmap (tokens.npy) で、実使用の増分は `free` で約 8GB だった【実測】。上限 30GB の範囲に収まっている。

### 2.3 n-gram 次数別 (全体)

| 次数 | アクセスの割合 | LRU 16GB | LRU 32GB | LRU 64GB | static 64GB |
|---|---|---|---|---|---|
| 2-gram | 30.4% | 97.3% | 98.1% | 98.3% | 92.5% |
| 3-gram | 33.9% | 90.8% | 92.9% | 93.6% | 79.5% |
| 4-gram | 35.7% | 85.0% | 88.6% | 90.2% | 73.1% |

- lookup の数は次数ごとに同じ (8 head ずつ) である。2-gram はチャンク内でよく重なるので、重複除去後の割合が小さい。
- ミスの大半は 3-gram と 4-gram から出る。

### 2.4 TP rank 別 (各層の行を ceil(N/2) で 2 分割)

| rank | 載る表 | lookup の割合 | 重複除去後の割合 | 共有 LRU 16 / 32 / 64GB | rank 別 LRU (K/2 ずつ) 16 / 32 / 64GB | rank 別 static 16 / 32 / 64GB |
|---|---|---|---|---|---|---|
| 0 | 2-gram ×8 + 3-gram head 0-3 | 50.0% | 47.3% | 95.0 / 96.3 / 96.6% | 96.1 / 96.6 / 96.6% | 86.9 / 87.9 / 87.9% |
| 1 | 3-gram head 4-7 + 4-gram ×8 | 50.0% | 52.7% | 86.9 / 90.0 / 91.3% | 85.2 / 88.4 / 91.1% | 64.4 / 70.5 / 75.2% |

- **miss IO の割合は rank 0 が 25%、rank 1 が 75%** (共有 LRU 16 / 32 / 64GB のどれでも同じ)。1 トークンあたりでは、32GB で rank 0 が 0.67 IO、rank 1 が 1.99 IO になる【実測】。
- 層 1 と層 14 の IO は 50:50 である。
- 対策
  - 行の取得を rank ごとに行わず、1 つのホスト側サービスで両 rank 分をまとめて取得する。
  - あるいは、ホストのキャッシュと NVMe 上の配置を行 ID の奇偶などで 2 分し、GPU 側の shard と切り離す。
  - GPU に送る量は 1 トークン 12.4KiB と小さいので、どちらの方法でも PCIe の負担にはならない。

### 2.6 ミス行の再利用率

ミスした行が、後で何トークン以内に再びアクセスされたか。距離は Engram 対象トークンで数えた。

| 方式 | 容量 | 区分 | ≤8k | ≤128k | ≤1M | ≤10M | >10M | トレース内で二度と無い |
|---|---|---|---|---|---|---|---|---|
| LRU | 16GB | prefill | 9.5% | 15.0% | 8.1% | 13.7% | 3.0% | 50.7% |
| LRU | 16GB | decode | 6.4% | 10.1% | 8.3% | 12.9% | 3.6% | 58.6% |
| LRU | 64GB | prefill | 9.6% | 16.0% | 7.3% | 9.8% | 3.3% | 54.0% |
| LRU | 64GB | decode | 6.2% | 9.6% | 7.5% | 11.6% | 3.9% | 61.3% |
| static | 64GB | prefill | 33.5% | 23.8% | 11.4% | 8.3% | 1.2% | 21.9% |
| static | 64GB | decode | 23.7% | 15.2% | 10.1% | 10.3% | 2.2% | 38.5% |

- static でミスした行の 57% (prefill) は、128k トークン以内にまた使われる。静的表では救えないが、LRU なら救える行である。
- LRU でミスした行の半分以上は、その後二度と使われない。ミスのたびに必ずキャッシュに入れると、キャッシュを汚す。
  - 32GB で足りているので急ぎではない。容量を減らしたい場合は、2 回目のアクセスで入れる方式 (TinyLFU や 2Q) の効果が見込める【推測】。
- ≤8k の割合 (約 6〜10%) は、同じ要求の中ですぐまた使われる行である。ミスを読み込み中の間は待ち合わせて、重複した IO を出さない (in-flight の合流)。

## 3. 導出値

### 3.1 RAM 行キャッシュの推奨サイズ

- **LRU (CLOCK) 32GB を推奨する。** 1.21 億行 × 264B に、索引 (行 ID → スロット、約 8〜12B/行) の 1〜1.5GB が加わり、実 RAM は約 34GB になる【計算】。
  - 16GB でも prefill 97.2%、decode 84.0% が出る (IO/token は 0.87 / 7.68)。RAM が足りないときの下限になる。
  - 48GB 以上は効果が 1 ポイント未満で、勧めない。RAM は prefix cache の host 層や pinned バッファに回す方がよい。
- PLAN の D3 の RAM 66GB は、約 34GB に減らせる。

### 3.2 prefill の IO/token

| 構成 | IO/token | 230k IOPS での prefill 上限 |
|---|---|---|
| キャッシュ無し (D1) | 31.2 (元の配置では ×1.0625 で 33.2) | 7.4k tok/s |
| page4K LRU 64GB (mmap + ページキャッシュ) | 1.11 | 207k tok/s |
| row static 64GB | 3.97 | 58k tok/s |
| row LRU 16GB | 0.87 | 265k tok/s |
| **row LRU 32GB** | **0.58** (未見タスクでは 0.68、日本語では 1.80) | **約 40 万 tok/s** |

- 1 本の prefill を 9k tok/s で流しても、平均 5.2k IOPS、p99 の要求でも約 10 万 IOPS で済む【計算】。

### 3.3 decode c16 の 1 step あたり IO

前提は PLAN §1.4 と同じく、1 step で 16 本 × 4 トークン = 64 トークンを検証する。却下されたドラフトのトークンも lookup する。

| 構成 | IO/token | **IO/step (64 トークン)** | IO/s (13.4 step/s 時)【計算】 | 層 1 分だけ (半分) をすべて IO 待ちにした場合の時間 |
|---|---|---|---|---|
| キャッシュ無し | 48.0 | 3,070 | 41k | 約 6.7ms + 遅延 |
| row static 64GB | 12.06 | 772 | 10k | 約 1.7ms |
| row LRU 16GB | 7.68 | 492 | 6.6k | 約 1.1ms |
| **row LRU 32GB** | **5.97** | **382** | **5.1k** | **約 0.83ms + 0.1〜0.3ms** |

- 13.4 step/s は、c16 合計 600 tok/s ÷ (16 本 × τ 2.8) から出した。
- 層 14 の分は、層 0〜13 の計算に隠れる。
- 層 1 の分は、ドラフト確定の直後に IO を出せば、大部分を層 0 の計算と重ねられる。step 時間は約 75ms なので、残る待ちは 1% 前後になる【計算】。
- GPU に送る量は 1 step 64 × 48 × 264B = 0.81MB。

## 5. 限界と注意

- **トラフィックの性質**
  - 測ったのは GLM-5.3 の 9 日分の要求で、91.8% が tools 付きのコーディングエージェント (ベンチ用の harness を含む) である。
  - 一般的な対話や RAG のように、新しい文書を大量に入れる用途ではヒット率は下がる。§2.9 の裾の値と、§2.7 の cold 率が参考になる。
- **出力の内容**: decode の対象は、GLM の出力を V4.1 の形式でレンダリングし直したものである。V4.1 自身の出力とは中身が違う。統計的な性質 (英語の推論文、DSML のツール呼び出し) は近いと考えている【推測】。
- **prefix cache**: 上限なしでセッションをまたいで共有すると仮定した。prefix cache が追い出されると、prefill のトークンが増える。増えるのは既に見た内容なので、ヒット率は上がる方向に動く。
- **同時実行**: 要求は到着時刻順に、1 件ずつ prefill と decode を通して処理した。実際の c16 の交錯は、再利用距離を数万トークン程度ずらすだけである。キャッシュ容量 (数千万行) に対しては小さい【推測】。
- **ドラフト**: DSpark の却下されたドラフトのトークンは、受理されたトークンと同じミス率と仮定した。step 間でのドラフトの重複も無視した。
- **ページ方式の前提**: page4K の方式は scale テンソル (6.1GB) が RAM に常駐すると仮定した。カーネルのページキャッシュは純粋な LRU ではない。readahead を止めないと、さらに悪くなる。
- **LRU の管理費**: LRU はアプリ側で、ロック無しの CLOCK 近似で実装する前提である。1 トークン 48 回のハッシュと、表の参照の CPU 負担は小さい【推測】。

## 6. 再現手順

```bash
cd tools
# 1) ログ -> V4.1 トークン列 (20 プロセス、約 2 分)
./.venv/bin/python -I x2_extract.py $GLM53/dump/reqlog work/x2/req 20
# 2) 時刻順に並べ、prefix cache (256 ブロック) を通し、テキストを分類 (28 並列で約 10 秒)
./.venv/bin/python -I x2_prep.py work/x2/req work/x2/prep 256
# 3) ハッシュを第 1 ラウンドの実装と照合
./.venv/bin/python -I x2_check_hash.py work/x2/prep
# 4) シミュレーション (64 パーティション全部、6 並列、約 8 分、実使用 RAM の増分 約 8GB)
./.venv/bin/python -I x2_sim.py work/x2/prep work/x2/sim_full.json 64 $(seq -s, 0 63) 6
# 5) 表を出す
./.venv/bin/python -I x2_report.py work/x2/sim_full.json work/x2/prep
```

- ファイル
  - `tools/x2_survey.py`: ログ構造の集計 (事前調査)。
  - `tools/engram_sim.py`: 第 1 ラウンドのハッシュ実装のコピー。`x2_sim.py` が import する。
  - 中間データは `work/x2/req` (2.3GB) と `work/x2/prep` (2.8GB)。
