# R3: 量子化後も日本語性能を保つための計測と手法 (DeepSeek-V4.1-Flash-1017)

作成日: 2026-10-18
対象: `deepseek-ai/DeepSeek-V4.1-Flash-1017` を ds41rt 0-spark + EXL3 K2 (平均 2.0〜2.2bpw) で動かす計画 (DECISION.md の E3)。
前提資料: `PLAN.md`、`DECISION.md`、`r2_quant_tools.md`、`r2_ds41rt.md`、`r2_lil_lowbit.md`、`r2_engram_hit.md`、`arch_spec.md`。同時期の `r3_qad.md` (QAD の可否) と `r3_routing_skew_measured.md` (routing の偏りの実測) とも整合をとった。
凡例: 【実測】はこの調査で手元で確かめた値、【資料】は出典付きの値、【計算】は式から出した値、【推測】は根拠が間接的な値。
GPU は使っていない。docker コンテナには触れていない。取得したのは 7MB 未満の評価用データだけである。

この調査で作ったもの

- スクリプト: `tools/r3ja/` (`r3ja_survey.py` 要求ログの言語集計、`r3ja_join.py` 分類と出力言語、`r3ja_outtok.py` 出力トークンの内訳、`r3ja_tasks.py` タスク単位の集計、`r3ja_engram_norm.py` Engram 正規化の日本語への影響、`r3ja_zhmix.py` 簡体字混入の検出、`r3ja_dsets.py` 評価セットのトークン長)。実行は `tools/.venv/bin/python -I <script>`。
- 集計結果: `work/r3ja/` (`agg.out`、`join.out`、`tasks.out`、`outtok.out`、`engram_norm.out`)。`rows.jsonl` は要求ごとの先頭 400 字を含むので、外に出さないこと。
- 評価データ (取得済み、計 6.6MB): `work/r3ja/data/` (JCommonsenseQA val、JamC-QA test/dev、MMLU-ProX ja、JHumanEval、MGSM ja、JSQuAD val、ELYZA-tasks-100、M-IFEval-Ja、Japanese MT-Bench の設問)。

## 0. 結論

1. **日本語は、このユーザーの運用では「指示と回答の言語」であり、トークン量の主役ではない。**
   - 要求の 92.2% (28,143/30,526) は利用者の発話が日本語で、タスク (最初の発話で数えた 3,951 種) でも 91.3% が日本語だった【実測】。
   - 一方、トークンで見ると日本語は少ない。Engram の対象区間 (新規 prefill と出力) のうち日本語は 10.9%、コードが 49.4%、その他 (英語の推論文、ツール JSON) が 39.7% である【実測、x2 の `prep_stats.json`】。
   - 出力 1,770 万トークンの内訳は、英語の推論 56.8%、ツール呼び出し 26.7%、**日本語の回答本文 14.0%**、日本語の推論 1.9% だった【実測、GLM-5.3 の出力】。
   - したがって守るべきものは「日本語の指示を正しく読んでコードとツールを動かす力」と「最後に返す日本語の回答」の 2 つである。校正と評価はこの 2 つに合わせて組む。
2. **文献では、低ビット量子化は日本語など非ラテン文字の言語をより大きく劣化させる。自動評価はその劣化を過小に見せる。**
   - Command R+ (103B) の W4 で、日本語の自動評価の低下は平均 1.7% だったが、人手評価では 16.0% 下がった。MGSM 日本語は 63.0→56.1 (−10.9%) だった【資料、Marchisio et al. 2024】。
   - 校正データを評価言語に合わせると、その言語の劣化が最も小さくなる。ただし狭い校正は活性の範囲を狭め、別の言語を悪化させることがある【資料、Chimoto et al. 2026】。
   - 公開されている sudoingX の校正データでは、仮名は全文字の 0.06% しかない【資料、r3_qad §4.1】。公開データのまま校正すると、日本語が「校正の薄い領域」になる。
3. **V4.1 / 1017 の日本語性能の公開値は見つからなかった。**
   - 技術報告の base モデル表には MGSM 80.2 (V4-Flash 85.7、V4-Pro 84.4)、MultiLoKo 45.5、C-Eval 92.1 がある【資料、TR Table 1】。多言語数学は前世代より低い。
   - 1017 のモデルカードと post-training の評価は、推論、コード、エージェントだけである。
   - したがって **日本語の基準は自分で測る必要がある。** 教師は参照ハーネス (1017 原重み) である。
4. **評価は 2 段で行う。** 1 段目はハーネスでの teacher-forced 採点、2 段目は量子化版サーバーでの生成タスクである (§3)。
   - 1 段目は 1 版あたり約 3 時間 (GPU 1 枚)、2 枚で並べれば約 1.5 時間かかる【計算、ハーネス実測 4,096 トークンで 52〜61 秒】。
   - 2 段目は 1 版あたり約 1.5〜2 時間かかる (judge を除く)【推測】。
   - ハーネスの生成は 1.4〜1.75 tok/s しか出ない【実測、`work/teacher/greedy3.json`】。そのため、原重みの生成結果を基準にした比較は小さな集合に限られる。生成タスクでの劣化は、版どうしの比較と、教師による on-policy 採点で見る。
5. **日本語を守る手段の優先順位は次のとおり。**
   - (a) 校正データの約 4 割を日本語が主の系列にする (§7)。量子化を Hessian 校正 (r3_qad の L1) に進めるときに必須である。
   - (b) routing の頻度を日本語系列で別に集計し、日本語で熱い experts を K3 側に寄せる (§4.2)。
   - (c) 局所蒸留 (r3_qad の L2) の損失で、日本語トークンの重みを上げる。
   - (d) Engram は FP8 のまま変えない。Engram の正規化は日本語の濁点と半濁点を区別しない (が=か、で=て) ことを確かめた【実測】。実装を作り直すときにこれを「直して」はいけない。
   - (e) 評価の条件 (reasoning effort、temperature、thinking の言語) を実運用に合わせる。
6. **「元の 1017 より日本語が良くなる」量子化は、教師に合わせる限り原理的に得られない。** 量子化以外の手段で狙えるものは 3 つある。
   - 運用の設定: reasoning effort、言語の指示、medium など非対応の effort の扱い。品質の上積みは小さいが、費用は掛からない。
   - DSpark の日本語での受理率を上げること。品質ではなく速度の向上である。
   - 日本語 LoRA / SFT。この機材では学習経路が無く、ds41rt にも LoRA の経路が無いので、勧めない (§4.7)。
7. **合格基準の案は §6 にまとめた。** 中心は 3 つである。
   - 日本語系列の KL が、同じ版の英語系列の KL の 1.3 倍以内に収まること。
   - 知識系 MCQ (JamC-QA、JCommonsenseQA、MMLU-ProX ja) の教師との差が、それぞれ 3.0 / 1.5 / 2.5 点以内に収まること。
   - 日本語の指示に日本語で答える率が 99% 以上、簡体字混入が 1% 以下であること。

**この案件への読み替え【推測】**

- 2bit 級は文献の 4bit より強い量子化なので、日本語の劣化は文献の値より大きくなる可能性が高い。
- 数学と推論が最も落ちやすく、選択式の判別タスクは落ちにくい (Marchisio)。日本語の評価を MCQ だけで済ませると、劣化を見落とす。
- 人手評価で初めて見える劣化 (不自然な言い回し、語の選択の誤り、文体の崩れ) がある。LLM judge による評価と、日本語固有の自動チェック (§3.4) を併用する。
- 端の層は言語固有なので、層別のビット配分で端の層を厚くすることは日本語にも効く見込みがある。

### 1.2 語彙とトークナイザ

【実測、`tools/r3ja/r3ja_engram_norm.py`、`r3ja_join.py`】

- 語彙は 129,280。仮名か CJK 漢字を含むトークンは 36,085 個ある (中国語用を含む)。長さは 2 文字が最多 (20,531 個) である。
- **日本語は 1 トークンあたり 1.88 文字、英語は 3.70 文字**だった。GLM の日本語回答 428 万字と、英語の推論 3,598 万字で測った。研究メモ (`research/*.md` など 30 本、54 万字) では 1.91 文字/トークンだった。
  - 同じ内容でも、日本語はトークン数が多く、誤りが入り得る位置も多い。KL はトークンあたりの値に加えて、100 文字あたりの値も出す (§6)。
  - 例: 「日本の首都は東京です。」は 6 トークン、"The capital of Japan is Tokyo." は 7 トークン。短い文では差が小さい。
- **Engram の圧縮語彙は、日本語の濁点と半濁点を落とす。**
  - 圧縮は NFKC→NFD→StripAccents→Lowercase の順に正規化する (`inference/engram.py:27-38`)。NFD が「が」を「か」と結合用濁点に分解し、StripAccents が濁点を消す。
  - その結果、が=か、で=て、ば=ぱ=は、ます=まず、ズ=ス、ド=ト などが同じ圧縮 ID になる。表層形の違うトークンがまとめられた日本語トークンは 131 個で、ほとんどが高頻度の助詞と仮名 1 文字である。
  - 学習時からこの仕様なので、品質の問題ではない。ただし、日本語では Engram の n-gram キーが英語より粗く、曖昧さの解消を本体 (experts と注意) が多く担っている可能性がある【推測】。そうであれば、日本語は experts の量子化に敏感になる。
  - ds41rt は Engram の圧縮を HF の `tokenizers` と同じ Rust 正規化器で作る (`ext/ds41rt/rust/crates/ds41rt-loader/src/engram_tokenizer.rs:81-111`)。`scripts/qualify-ds41-engram.py` で公式との一致を確かめられる。参照する `inference/engram.py` の sha256 は 1017 と一致した【実測、`docs/ds41-reference-lock.json`】。
- Engram の IO は日本語で多い。prefill の IO/token は、行 LRU 32GB で日本語 1.80、コード 0.59 だった (約 3 倍)【資料、r2_engram_hit §2.5】。これは速度の問題で、品質には影響しない。

## 2. ユーザーの GLM 実トラフィックに含まれる日本語

### 2.1 方法

- 入力: GLM 時代の要求ログ (173 ファイル、19GB。コーディングエージェント型の実トラフィック、複数のクライアント) の `request.received.openai` 31,914 件と、X2 で V4.1 トークン化済みの `work/x2/req` (30,526 件、meta.json の `plen` / `olen`)。
- 言語判定: 仮名が 3 字以上あり、仮名と漢字が非空白文字の 10% 以上なら日本語とした。仮名が無く漢字が 20% 以上なら中国語とした。利用者の発話からは `<system-reminder>` を除いた。
- 分類: system prompt の先頭 400 字のハッシュでクライアントを分け、最初の利用者発話の書き出しで細分した (`r3ja_join.py` の `cat()`)。
- 出力の内訳: V4.1 の出力トークン列を `</think>` (id 128822) で推論と本文に分け、本文はさらに DSML のツール呼び出しの前後で分けた。
- 所要: ログの走査 38 秒 (6 並列)、出力の復号 44 秒【実測】。

- GLM の日本語回答 9,180 件のうち、簡体字専用の漢字 (EUC-JP で表せず GB2312 で表せる字) を 1 字以上含むものは 0.47%、3 字以上は 0.10% だった【実測、`r3ja_zhmix.py`】。量子化版を評価するときの比較の目安にする。

### 2.4 トラフィックから読み取れること

- 日本語の能力のうち、量子化で失いたくないものは次の 4 つに分かれる。
  - 日本語の仕様 (指示、docstring、レビュー観点) を読み、英語の推論とコードとツールに変換する力 (A 群、要求の 68%)。
  - 説明、計算、計画、比較などの日本語の回答 (B 群、新規 prefill の 41%)。
  - 字数や文体の制約がある短い日本語 (C1、G)。
  - 日本固有の知識 (B 群の一部。JamC-QA が近い)。
- A 群は同じ評価用の harness を繰り返し流したもので、タスクの種類は少ない (A0 は 36 種)。要求数の重みは実際の多様性より大きく見える。そのため、§5 の重みは要求数、出力トークン、タスク種類の 3 つを見て決めた。

## 3. 日本語評価セットの選定 (2 段構成)

### 3.1 2 段に分ける理由

- **1 段目 (ハーネス、teacher-forced)**: 原重みの教師と量子化版の学生に同じトークン列を通し、位置ごとの分布を比べる。
  - 同じ入力で比べる対の比較なので、少ない量で差が出る。
  - ds41rt の API には logprobs が無い (r2_ds41rt §7) ので、分布の比較はハーネスでしかできない。
  - ハーネスは 4,096 トークンの系列 1 本を 52〜61 秒で通す (agent24 の 24 本で実測、`work/teacher/teacher.log`)。短い系列でも 1 回の forward に約 7 秒かかる (`greedy3.json` の prefill 6.8〜7.3 秒)。短い設問は 4,096 トークンに詰めて流す。
- **2 段目 (ds41rt、生成)**: 量子化版を実運用と同じ API で動かし、生成の正誤、指示の順守、言語の一貫性を見る。
  - 原重みの生成はハーネスで 1.4〜1.75 tok/s しか出ないので、2 段目の基準にはできない。基準は §3.5 の方法で補う。

- 外部の強いモデル (Swallow は `gpt-5.2-2025-12-11` を使う) が最も信頼できる。送るのは公開ベンチの設問と量子化版の回答だけにする。

- 量子化版自身を judge にすると、自分の出力を好む偏りが出る。版どうしの比較に限り、位置を入れ替えた対比較として使える【推測】。

## 4. 日本語を守る手段と伸ばす手段

### 4.1 日本語を多く含む校正データでの Hessian 校正

- 現在走っている量子化は H=I (校正なし) なので、日本語が特に不利になることも有利になることもない (r3_qad §4.1)。
- Hessian 校正 (r3_qad の L1、exllamav3 の LDLQ、sudoingX の pass1) に進むと、校正データの言語が誤差の配り方を決める。EXL3 は H で重み付けした誤差を小さくするので、校正で頻繁に現れる入力方向の誤差が優先して削られる。
- 公開の sudoingX データだけでは日本語が薄く、日本語が相対的に悪化するおそれが高い (§1.1)。構成は §7 に示す。
- Chimoto らの失敗例 (狭い校正で活性の範囲が狭まる) を避けるため、日本語だけに寄せず、コードと英語と中国語を必ず残す。

### 4.2 日本語トークンでの routing 頻度に基づくビット配分

- 1017 の実トラフィック (エージェント 24 本) では、上位 25% の experts が routing の 69.1% を持ち、深い層ほど偏る (Gini 0.60)【資料、r3_routing_skew_measured.md】。公開値 (56%) より偏りが強い。
- 日本語系列だけで数えた頻度はまだ無い。ja16 の教師の実行で集計できる (§3.2 の分割が要る)。
- 配分の式の案【推測】:

```
importance(l, e) = sens(l) × Σ_d w_d × share(l, e, d)
  d ∈ {ja, code, agent-en, other}、w = {0.40, 0.30, 0.20, 0.10}
  share(l, e, d) = 区分 d で層 l の expert e が選ばれた割合 (per-token share)
  sens(l) = 層の感度 (sudoingX の p4_sensitivity と同じ測り方)
日本語の保護: share(l, e, ja) が層内の上位 5% で、かつ share_ja / share_all ≥ 2 の expert は K3 に固定する
```

- 予算: ds41rt の staged manifest で混ぜられるのは隣り合う 2 段 (K2 と K3) である (DECISION §3.4、r3_qad §5)。平均 2.2bpw なら K3 は experts の約 20% までになる【計算: 2 + 0.2 × 1 = 2.2、付加のスケールは無視】。日本語の保護枠が 5% を超えると他の枠を圧迫するので、日本語の保護は全体の 20% の内側で上位から採る。
- 層の扱い: 言語固有の routing は先頭と末尾の層に寄る (§1.1)。experts 別の頻度が揃う前の第一歩としては、層 0〜3 と 36〜39 の 8 層 (20%) を K3 にする層別配分が、日本語の根拠とも、LibertAIDAI 3.5bpw の配分 (端の 20 層を K4) とも整合する【推測】。ただし ds41rt の raw 経路は `layer_bits` を拒否するので (r2_ds41rt §2)、層別でも staged manifest が要る。
- DSpark は層 37〜39 の入力を使うので (`model.py:1268-1269`)、末尾の層を厚くすることは受理率の維持にも効く見込みである【推測】。

### 4.3 日本語系列での局所蒸留

- r3_qad の L2 (層ごとに suh / svh と shared expert を、教師の MoE 出力に合わせて学習する) の損失で、日本語トークンの重みを 2 倍にする。
- 局所蒸留の目標は教師の出力なので、到達できる上限は 1017 と同じである。日本語に重みを寄せると、量子化誤差の予算が日本語側に移り、英語とコードの誤差が少し増える【推測】。§6 の対照 (en-neutral、code) が悪化しないことを必ず確かめる。
- ds41rt は suh / svh を checkpoint の値のまま expert ごとに読み込むので (`v41_exl3_residency.rs:233-290`、r3_qad §2.3)、推論の追加費用は無い。

### 4.4 Engram (FP8 のまま)

- Engram を外すと、事実知識系の性能は 29〜44% しか残らない (ET §1.3)。PPL も code 1.87→4.16、prose 6.43→9.06 に悪化する (WE §3.1)。日本固有の知識 (JamC-QA) を守るうえで、Engram を FP8 のまま残す判断は変わらない。
- 日本語では Engram の役割が英語と違う可能性がある。
  - n-gram キーが濁点を区別しない (§1.2)。
  - 8k チャンク内で行が重複しにくい (unique 0.79、コードは 0.65)。ヒット率も低く、IO は約 3 倍になる (r2_engram_hit §2.5)。
  - どちらも品質の損失ではないが、日本語では「Engram に覚えさせた知識を、本体が文脈に合わせて解釈する」比重が大きい可能性がある【推測】。
- 実験で確かめる案 (PLAN X10 の日本語版): 1 段目の JA-KL と JamC-QA を、Engram を有効にした原重みと、Engram の出力を 0 にした原重みで比べる。日本語の落ち幅が英語より大きければ、日本語は Engram にも experts にも敏感だと分かる。ハーネスでの追加は 1 回分 (約 3 時間) である。
- Engram の表を変える案 (MXFP4 化など) は、日本語の評価で FP8 と差が無いことを確かめるまで採らない。

### 4.5 チャットテンプレート、reasoning effort、sampling

- 評価の条件は実運用に合わせる。
  - A 群と F 群: thinking、effort high (V4.1 の既定は high = 75。`encoding.py:448-453`)。
  - B 群: thinking、effort high。medium は proxy で写す (§2.3)。
  - C 群と G 群: thinking、effort low (= 50)。
  - temperature は、回帰の比較では 0 (greedy)、最終確認では推奨値 1.0 / top_p 1.0 と、運用値 0.6 の両方で回す。量子化の誤差は確率の低いトークンの選ばれやすさを変えるので、温度が高いほど言語の切り替わりや誤字が出やすくなる可能性がある【推測】。
- 1017 の `encoding.py` は 0909 と sha256 が違うが、OpenAI 形式の入力では出力が完全に一致した (r2_ds41rt §2.2)。日本語の多ターンとツール結果で終わる会話を、その比較に 1 件足しておく。
- 日本語の知識問題では、effort を max (100) に上げると正答率が上がる可能性がある。量子化による劣化の一部を推論の量で補う使い方になる【推測】。速度とのトレードオフなので、§3.3 の JamC-QA を high と max で比べて判断する。

### 4.6 DSpark の受理率 (日本語での低下)

- ds41rt の公表値 (C1、2 RTX) では、受理率は code 88.05% (1 round 5.19 トークン)、topic 57.82% (2.62)、multilingual (繁体字中国語) 56.30% (2.73) で、C1 の速度は code 225.20、multilingual 104.32、topic 99.31 tok/s だった【資料、r2_ds41rt §5.2】。
- 日本語の自然文も topic や multilingual に近い 2.3〜2.8 トークン / round になり、c1 は 90〜110 tok/s 程度になる見込みである【推測】。
- 量子化版では、drafter は原モデルに合わせて学習されているのに、検証する本体が量子化でずれる。そのため受理率はさらに下がる。下がり方は、本体の top-1 一致の低下にほぼ比例すると見る【推測】。日本語の top-1 一致が英語より低ければ、日本語の受理率は英語以上に下がる。
- 測り方: ds41rt の `/v1/stats` は集計値なので、日本語だけの負荷 (ELYZA、B 型の質問) とコードだけの負荷を別々に流して比べる。
- 対策の候補 (§4.7 の表の 3 行目): drafter の dense 部分を、量子化版本体の日本語出力に合わせて追加学習する。

### 4.7 「向上」の選択肢 (MIT ライセンス)

| 案 | 中身 | 見込み | 費用 | 判断 |
|---|---|---|---|---|
| 運用設定 | 日本語の system prompt で回答言語と文体を指定する。effort を区分ごとに選ぶ。medium の写し方を決める | 言語の一貫性が上がる。品質の上積みは小さい【推測】 | 0 | **採る** |
| 日本語に重みを寄せた校正と蒸留 | §4.1〜4.3 | 一律量子化と比べて日本語の劣化が減る。1017 は超えない | r3_qad の L1 / L2 に含まれる | **採る** |
| DSpark の日本語追加学習 | 層 37〜39 の入力 (1 トークン 15,360 次元 bf16 = 30KB) をハーネスで保存し、drafter の dense 部分 (main_proj、注意、Markov head、confidence head) を量子化版の日本語出力に合わせて学習する。experts は MXFP4 (`mtp_experts=source`) のまま残す | 日本語の c1 が 10〜25% 速くなる可能性【推測】。品質は変わらない (検証で落とすため) | 100 万トークンで隠れ状態 30GB。学習は 1 枚で数時間【推測】。ds41rt が書き換えた drafter の dense を読めるかは未確認 | 品質の判定 (G1) が済んでから検討する |

### 4.8 QAD、動的量子化、Tensorfold を日本語の側から見た要件

r3_qad が QAD の可否 (L0〜L4) と、動的量子化と Tensorfold との関係を扱っている。ここでは日本語の側から足す要件だけを挙げる。

- **QAD (L1〜L3)**: 校正と蒸留のデータに、§7 の日本語の比率を使う。損失の日本語トークンの重みを設定で持たせる。評価用の保留データ (要求ログの後半、技術文書の別ファイル) と混ぜない。
- **動的量子化**: 実行中に精度を切り替える仕組みは ds41rt に無い (r3_qad §5)。日本語の観点で意味があるのは、負荷に応じて「日本語で熱い experts を K3 にした構成」と「コードで熱い experts を K3 にした構成」を切り替える使い方である【推測】。
  - 1,536 experts を K2 から K3 に入れ替えると、K3 の expert 1 個は 3,540 万 param × 3bit ≒ 13.3MB なので、計約 20GB をホスト RAM から送ることになる。PCIe 約 20GB/s/枚なら 2 枚で約 0.5 秒かかる【計算】。
  - VRAM の予算は増やせないので、上げる分と同じだけ別の experts を下げる必要がある。どの engine にも実装は無い。
- **Tensorfold 系の形式を設計する場合**: manifest に次の 3 つを持たせる。
  - expert ごとの区分別の routing 割合 (ja、code、agent-en、other)。配分を後から再現し、見直せるようにするためである。
  - 校正データの構成 (区分と比率、トークン数、保留データの識別子)。
  - 区分別の評価結果 (JA-KL の KL と top-1 一致、MCQ の差)。版を比べるときに、日本語の劣化が増えていないかを一目で確かめられる。

## 5. 日本語評価の重み付け (トラフィックからの提案)

§2.3 の 3 つの尺度は大きく違う。要求数では A 群が 68% を占め、新規 prefill では B 群が 41%、タスクの種類では C1 が 50% になる。A 群は同じ harness の繰り返しなので、要求数だけで重みを決めると A 群に寄りすぎる。C1 は短い出力 (出力トークンの 0.3%) なので、タスク種類だけで決めると C1 に寄りすぎる。そこで 3 尺度の中間をとった【推測】。

| 能力 | 重み | 対応する評価 (重みの内訳) | トラフィック上の根拠 |
|---|---:|---|---|
| 日本語の指示によるコーディングエージェント | 40% | A0 型の再生 20%、JHumanEval 10%、J-agent の KL 10% | 要求 68%、出力 75%、新規 prefill 34% |
| 日本語の汎用アシスタント (説明、計算、計画、比較) | 25% | ELYZA-tasks-100 8%、B 型の質問 (judge と on-policy KL) 8%、MGSM ja 5%、Japanese MT-Bench 4% | 要求 17%、新規 prefill 41% |
| 日本固有の知識と読解 | 10% | JamC-QA 5%、JSQuAD 2%、JCommonsenseQA 1.5%、MMLU-ProX ja 1.5% | B 群の一部 (説明や比較の質問) |
| 短い日本語と形式の指示 | 10% | C1 型の状況要約 5%、M-IFEval-Ja 5% | 要求 8% (C)、タスク種類 57% (C と G) |
| 日本語の指示によるツール操作 | 10% | ツール評価の日本語版 5%、D 型の操作の再生 5% | 要求 4% (D)、ツール付きが 92% |
| 英語とコードの対照 | 5% | HumanEval、英語の KL | 要求 2% (E)。日本語に寄せた調整の副作用を見る |

- 重みは総合点を作るためのもので、合否は §6 の個別の基準で決める。総合点だけで判定すると、小さい重みの区分での大きな劣化 (例えば言語の切り替わり) を見落とすからである。
- タスクの構成は時期で変わる。四半期ごとに `r3ja_survey.py` と `r3ja_join.py` を回し直して重みを更新する。

## 6. 推奨の日本語評価プロトコルと合格基準 (案)

### 6.1 手順

1. **教師の取得 (1 回)**: JA-KL 70 本と MCQ 123 本をハーネスで通す。GPU 1 枚で約 3 時間、2 枚で約 1.5 時間。区分ごとに別の実行にして、区分別の routing 頻度も保存する。
2. **版ごとの 1 段目**: 同じ 193 本を `--exl3-pack` を付けて通す。約 3 時間 (1 枚)。
3. **版ごとの 2 段目**: ds41rt で §3.4 の生成タスクを回す。約 1.5〜2 時間。日英の対 (§3.5 b) を含める場合は約 1 時間足す。
4. **on-policy 採点**: 2 段目の ELYZA と B 型の出力から 8 本を作り、教師と学生の両方で採点する (1 段目に含まれる)。
5. **judge**: 外部 judge か、ハーネスの原重みを judge にする (§3.5)。
6. **報告**: 区分別の KL、top-1 一致、ΔNLL、100 文字あたりの KL、MCQ の差と McNemar 検定、生成タスクの得点、§3.6 のチェックを、版ごとに 1 表にまとめる。

GPU の順序: ハーネスと ds41rt は同時に動かせないので、2 段目を先にまとめて回し (版ごとに ds41rt を起動し直す)、その後に 1 段目をまとめて回すと、切り替えの回数が少ない。

### 6.2 合格基準 (案。DECISION §4.2 の G1 に日本語の項目を足す)

| ID | 指標 | 基準の案 | 根拠 |
|---|---|---|---|
| G-JA1 分布 | JA-KL の区分ごとの KL / 同じ版の en-neutral の KL | 1.3 以下 | sudoingX の multilingual は 1.34 倍だった。日本語を校正に入れれば閉じる (§1.1) |
| G-JA2 分布 | 日本語区分の top-1 一致 | en-neutral の top-1 一致 − 2 点以上 | 2.0bpw 一律の neutral は 80.4%、code 88.5%、agentic 94.7% (r2_quant_tools §5)。日本語が neutral を大きく下回らないこと |
| G-JA3 知識 | 教師との正答率の差 (対の比較) | JamC-QA 3.0 点以内、JCommonsenseQA 1.5 点以内、MMLU-ProX ja 2.5 点以内 | §3.3 の統計で見分けられる幅。JamC-QA は知識依存で落ちやすいので幅を広くした |
| G-JA4 生成 | JHumanEval、MGSM ja、ELYZA、MT-Bench (日本語) | 日英の比 (日本語の得点 / 英語の得点) が v0 より悪化しない。原重みの小さな基準 (§3.5 c) か公式 API と比べられる場合は、低下 3 点以内 (DECISION の「日本語 QA の低下 ≤3 点」) | 原重みの生成が取れないため |

| G-JA7 形式 | C1 型の字数と文体の順守、M-IFEval-Ja (strict) | C1 は 95% 以上。M-IFEval-Ja は IFEval (英語) との差が v0 より広がらない | 短い出力の崩れは利用者に直接見える |

## 7. 校正データの構成 (比率)

総量は 50〜60 万トークンとする。sudoingX の pass1 は 85.3 万トークンで 1 層あたり約 49GiB を使う (r2_quant_tools §1.3) ので、60 万なら約 35GiB で GPU 1 枚に収まる【計算】。

区分は、系列の採点区間 (出力側) の主な文字種で分ける。A 群の系列は日本語の指示とコードとツール結果を含むので、文字種で日本語が 25% 以上の窓を「日本語が主」に、それ以外を「コードとエージェント」に入れる。

| 区分 | 比率 | トークン (60 万の場合) | 出典 | 備考 |
|---|---:|---:|---|---|
| 日本語が主: エージェント (A0〜A2、F) | 14% | 8.4 万 | `work/x2/req` の前半 | 日本語の指示、docstring、レビュー観点を含む窓 |
| 日本語が主: アシスタント (B、D) | 12% | 7.2 万 | 同上 | 説明、計算、計画、比較、翻訳 |
| 日本語が主: 短い出力 (C1、C2、G) | 3% | 1.8 万 | 同上 | 字数と文体の制約がある出力 |
| 日本語が主: on-policy の推論と回答 | 5% | 3 万 | v0 の ds41rt で、日本語の質問 (評価に使わないもの) に答えさせる | V4.1 自身の推論の言語と文体を入れるため。GLM の出力は V4.1 の文体と違う |
| 日本語が主: 一般コーパス | 6% | 3.6 万 | 日本語 Wikipedia 3%、技術文書 2% (評価用とは別のファイル)、青空文庫 1% | 知識と書き言葉 |
| コードとエージェント (英語の推論、ツール JSON) | 32% | 19.2 万 | `work/x2/req` の code と other の窓、E 群、sudoingX の `conversations` のエージェント部分 | トラフィックのトークンの大半 |
| コード (単体) | 13% | 7.8 万 | `work/x2/req` の code 窓、sudoingX の code | |
| 英語の一般文と数学 | 8% | 4.8 万 | sudoingX の `conversations` / `instruct_v3` | |
| 中国語ほかの多言語 | 5% | 3 万 | sudoingX の多言語部分、MGSM の zh など (評価に使わない分割) | 活性の範囲を狭めないため (Chimoto らの失敗例)。V4.1 が中国語に切り替わる経路の誤差も抑える |
| 画像を含む系列 | 2% | 1.2 万 | 要求ログの画像付き要求 (259 件) | `bias_vl` の経路を空にしない |
| **計** | **100%** | **60 万** | | 日本語が主の系列は 40% |

- r3_qad §4.2 の案 (日本語 30%、エージェント 30%、コード 20%、英語ほか 20%) とは、日本語の数え方が違う。r3_qad の「エージェント」には日本語の指示の窓が含まれる。この表では、日本語の指示の窓のうち日本語が採点区間の 25% 以上のものを日本語に数えた。両者は同じ方向の案である。
- 日本語が主の系列 40% は、トラフィックのトークン比 (日本語 10.9%) より多い。sudoingX の観察 (校正の薄い領域ほど劣化が広がり、データを足すと閉じる) に基づいて、日本語を薄い領域にしないためである。日本語に寄せすぎた副作用は G-JA10 で見る。
- **experts ごとの最低トークン数**: 60 万トークン × top-6 / 384 で、1 層あたり 1 expert 平均 9,375 回の routing になる【計算】。下位 30% の experts は routing の 3.7% しか持たない (r3_routing_skew_measured) ので、平均約 1,150 回、最も冷たい experts は数十回以下になる。MoEQuant の expert-balanced sampling (EBSS) のように、冷たい experts を通る系列を追加するか、sudoingX の「全トークンの事前分布を Hessian に足す」処理を使う。
- **保留データの分離**: 校正は要求ログの前半 (X2 と同じ切り方)、評価は後半から取る。同じタスク (最初の発話のハッシュ) が両方に入らないようにする。技術文書はファイル単位で分ける。

## 8. 未解決事項

- **V4.1 が日本語の指示に何語で推論するか。** GLM は 97.7% が英語だった。V4.1 が中国語で推論するなら、校正の中国語の比率と、簡体字混入の基準を見直す必要がある。ハーネスで thinking モードの日本語プロンプトを 3 件、300 トークンずつ生成すれば、約 10 分で見当がつく【計算: 1.4〜1.75 tok/s】。
- 日本語系列での routing の偏り (日本語で熱い experts がどれだけあるか)。ja16 の counts を区分別に分けて出す必要がある。
- A0 型の再生に使う元のタスク (リポジトリと受け入れテスト) が、どこに残っているか。要求ログには指示とツールの入出力だけがあり、作業ツリーそのものは無い。
- ハーネスの EXL3 学生の採点速度。教師と同じ 52〜61 秒 / 本と仮定した。
- 外部 judge と公式 API を使ってよいか (公開ベンチの設問だけを送る)。ユーザーの判断が要る。
- ds41rt が `medium` などの reasoning_effort をどう扱うか (拒否か、黙って既定にするか)。
- 日本語の dSpark 受理率の実測値。ds41rt の公表値は日本語を含まない。
- Engram を 0 にした原重みで、日本語と英語の落ち幅が違うか (§4.4 の実験)。
