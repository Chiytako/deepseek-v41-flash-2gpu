# R3: "Tensorfold" の特定と、1017 の routed experts への「折りたたみ」型圧縮の適用可否

作成日: 2026-10-18 (JST 10:20〜11:30)
対象: `deepseek-ai/DeepSeek-V4.1-Flash-1017` の routed experts (40 層 × 384 expert × w1/w3/w2、543.6B 重み、MXFP4 288.8GB)
前提資料: `PLAN.md`、`DECISION.md`、`r2_quant_tools.md`、`r2_ds41rt.md`、`r2_lil_lowbit.md`、`r2_engram_hit.md`、`arch_spec.md`
凡例: 【実測】は今回手元で測った値、【資料】は出典付きの値、【計算】は式から出した値、【推測】は根拠が間接的な値。
守ったこと: GPU は使っていない (CPU と numpy のみ、OpenBLAS は 8 スレッド)。稼働中のコンテナには触れていない。重みはダウンロードしていない。

スクリプトと出力

## 0. 結論

1. **"Tensorfold" という名前の圧縮手法・論文は見つからなかった。** この名前で実在するのは、**LLM 推論エンジン TensorFold** (ashhart/TensorFold) と、その DeepSeek-V4.1 向け fork 群である (§1)。
   - V4.1 系の fork は、2 台の DGX Spark (GB10) を RoCE でつなぐ TP2 構成を前提にしている。expert は EXL3 を混合ビットで持つ。
   - 1017 の routed experts にとって TensorFold が持つ意味は、圧縮手法ではない。「**expert ごとに混合ビットの EXL3 を読めるエンジン**」と、「**それ向けに作られた校正済み混合量子化レシピ** (Krishando 2.86bpw など)」の 2 つである。
2. **名前から想像される「折りたたみ」型圧縮 (expert 間の共有、共通基底 + 差分、テンソル分解、expert の統合) は、1017 では効かない。** 3 層 (3 / 20 / 37) の実データで、どの方式でも共有できる成分がほぼ無かった【実測、§2】。
   - **全 expert の平均 (共有成分)** が持つエネルギーは 0.26〜0.43%。expert どうしが独立なら 1/384 = 0.26% になり、ほぼこの値に一致する。
   - **平坦化した expert 間の cos 類似度**は、最大でも 0.008 だった。
   - **hidden 側 (5120 次元) の共有基底**を使っても、変換符号化の利得はガウス近似で 0.013〜0.044 bit/重みにとどまる。
   - **ニューロン単位** (w1 行 | w3 行 | w2 列) で他の expert の最近傍を探しても、|cos| の中央値は 0.05、最大でも 0.50 だった。等方的な乱数での基準値は 0.043 である。統合すると、エネルギーの 99% 以上が残差として残る。
   - **expert 単体の低ランク性**は、i.i.d. ガウス行列よりわずかに強い程度だった。rank 1024 (パラメータの 64%) でもエネルギーの 75% しか取れない。
   - 2bit 量子化のシミュレーションでは、どの折りたたみ方式も相対誤差の改善が 0.8% 以下だった。ビットに直すと 0.001〜0.010 bit/重みである。共有基底を bf16 で持つと 0.062 bit/重みかかるので、正味では損になる【計算】。
3. **1017 の experts は、重みの空間ではほぼ「独立な白色ガウス雑音」に見える。** EXL3 の tail-biting Viterbi (2bit で相対誤差 0.262) は、ガウスの R(D) 限界 (0.25) との差が約 0.065 bit しかない【計算】。
   - したがって、重みの MSE を基準にする限り、どんな変換や共有を足しても上積みは小さい。最大でも共有 KLT の 0.03 bit 程度である。
   - 品質を上げる余地は、次の 3 つにある。
     - (a) **どこにビットを配るか** (routing 頻度、感度、super expert の保護)
     - (b) **出力誤差を基準にした校正** (Hessian、E3-2)
     - (c) **QAD などの学習による回復**
4. **推奨: "Tensorfold 型" の圧縮形式は採らない。EXL3 の混合精度を本線にする。** 効果の大きさは次のとおりで、どれも折りたたみの 10〜100 倍になる。
   - E3-1 の Viterbi への再符号化: 0.53 bit 相当【計算: log2(0.3773/0.2616)】。VRAM の増分は無い。
   - expert ごとの K2/K3 配分 (150GB で 17% の expert を K3 にできる)【計算】
   - 校正 (公開値で KL 0.36 → 0.13〜0.20)【資料】
5. **TensorFold エンジンそのものも、本命 (ds41rt 0-spark) の代わりにはならない** (§4.1)。
   - 対応する通信路が GB10 の RoCE だけで、同時に処理できる系列は 1〜4 本である。
   - 既製の 2.9bpw パックは、experts だけで 182.6GiB あり、2 枚の VRAM に入らない。
   - 流用する価値があるのは、**混合幅 EXL3 の expert 表現と、Krishando 方式の校正手順**である。
6. **日本語について**: 折りたたみや統合は、routing 頻度で重み付けするため、使用頻度の低い言語を担う expert を最も削りやすい (§5)。日本語を守るには、次の 2 点を EXL3 の配分に入れるのが筋である。
   - 日本語コーパスで集計した routing 頻度を、ビット配分の重みに入れる。
   - 日本語の教師 (`work/teacher/ja16.jsonl`) で、KL を区分ごとに監視する。

### 1.2 「折りたたみ」型の MoE 圧縮の既存研究

**既存研究の限界 (当機の目的から見て)**【資料 + 推測】

- 報告されている圧縮率は 20〜60% である。比べている基準は BF16 / FP16 なので、ビットに直すと 16 → 6〜13 bit/重みに当たる。
- 当機で要るのは **MXFP4 4.25bpw → 約 2.1bpw** であり、BF16 から見れば 87% の圧縮になる。これは量子化の領域である。
- 折りたたみと 2bit 量子化を重ねたときの結果を示した研究は、KBVQ-MoE (3bit、小型モデル) くらいしか無い。

## 2. 1017 の experts で「折りたたみ」の余地を測る【実測】

### 2.1 方法

- 対象は層 3 (前段。ratio 2)、層 20 (中段。ratio 1 の書き込み元)、層 37 (後段。DSpark の入力を取る層)。それぞれ 384 expert × {w1, w3, w2} を測った。
  - shard はそれぞれ `model-00006` / `model-00023` / `model-00040` (層 L は shard L+3)。
- 逆量子化は、`I8` に詰めた E2M1 (低ニブルが偶数要素) × `F8_E8M0` (32 要素ごと) で行った。FP4 の値の表は `inference/convert.py:13-15` と同じである。
  - 実装は `r3_fold_measure.py:72-77`。合成データで参照実装と一致することを確かめた。
- 測った項目 (`r3_fold_measure.py:249-` の各段)
  - **A/B** 平均成分と expert 間の cos。384×384 の Gram を行ブロックごとに積み上げた。
  - **C** hidden 側 5120 次元の共有共分散 C = Σ_e (hidden 側の外積)。w1/w3 は入力側、w2 は出力側である。192 expert (1 つおき) で求めた。固有値スペクトルからは、次の 2 つを出した。
    - 高レート近似の変換符号化利得: 0.5·(mean log2 diag − logdet/n)。対角、32 / 128 / 512 ブロック、全 5120 の各場合について出した。
    - 2bit での逆注水の歪み比
  - **D** expert 単体の残差 (W_e − α_e·M) の特異値エネルギー。6 expert で測った。
  - **E** ニューロン単位 (15360 次元) の最近傍 |cos|。問い合わせは 768 本で、それぞれ他の 383 expert × 2304 ニューロン = 88.2 万本の中から探した。等方的な基準値は sqrt(2 ln(2N)/d) = 0.043。
  - **F** 2bit の量子化シミュレーション
    - 量子化器: EXL3 の `regularize` と同じ前処理 (出力 / 入力チャネルの RMS スケール、両側に符号付き 128 Hadamard、`exllamav3_5be8/.../exl3_lib/quantize.py:1185-1219`) に、ガウスの Lloyd-Max スカラー量子化を組み合わせた。
    - 比べた方式: 直接 2bit、平均 fold + 残差 2bit、共有 KLT5120 + 整数ビット配分、KLT128 + 配分、対角 + 配分。どれも平均 2.0bit に揃えた。
    - 注意: スカラー量子化は trellis より絶対値が悪い (2bit で 0.343 対 Viterbi の 0.262)。このため F は**方式どうしの相対比較**にだけ使う。

### 2.3 解釈

1. **重みの空間で見ると、1017 の experts は「互いに独立で、内部もほぼ白色」である。** 折りたたみ型の圧縮が当てにする冗長性 (expert 間の共有、共通の部分空間、低ランク性) は、どれも 1% のオーダーしか無い。
   - 推測される理由: 1017 の routed experts は MXFP4 で学習・公開されている。細粒度 (inter 2304) の 384 expert は、互いに専門化している。
2. **EXL3 Viterbi は、すでに理論限界の近くにいる。** 白色ガウスの源なら 2bit の R(D) 限界は相対誤差 0.25 で、Viterbi + refit は 0.2616 (sfxnz、`build/qrecipe/tools/requant_full.py:16`) である。差は 0.5·log2(0.0684/0.0625) ≒ **0.065 bit**【計算】。
   - これに共有 KLT の最大 0.03〜0.04 bit を足しても、上積みは 0.1 bit に届かない。
3. **一方、いま回している greedy beam16 の符号化は、相対誤差が 0.377** (`build/qrecipe/tools/requant_probe.py:3-6`。0909 での値) で、スカラー Lloyd-Max (0.343) よりも悪い。
   - Viterbi に変えるだけで、MSE が 2.07 倍良くなる。ビットに直すと **0.53 bit 相当**である【計算】。
   - **重みの空間でまだ取れる改善のうち、最大のものは E3-1 (Viterbi への再符号化) である。**
4. **ここで測ったのは重みの MSE だけである。** 実際の品質は、活性の Hessian H = E[xxᵀ] で重み付けした出力誤差で決まる。hidden 状態は強く偏っている (super expert、少数の巨大チャネル)。したがって「H で白色化した空間」では、共有の構造が見える可能性が残る (§7 の未解決 1)。
   - ただしその場合も、それを取り込む正攻法は、折りたたみではなく **Hessian 付きの校正 (E3-2)** である【推測】。

## 3. "Tensorfold 型" (折りたたみ型) を採る場合の仕様 (参考。採用は勧めない)

§2 で効果が無いと分かったので、ここでは「仮に作るなら」の仕様と、その費用を示す。比べる対象は、効果が最も大きかった **共有 KLT + 帯域ごとの混合 K** (以下 TF-fold) と、文献で最も一般的な **共有 base + delta** (以下 TF-delta) である。

### 3.1 データ形式

| 項目 | TF-fold (共有基底の回転 + 帯域ごとの混合 K) | TF-delta (共有 base + expert 差分) |
|---|---|---|
| 層ごとに共有するもの | `V_in[5120,5120]` (w1/w3 の入力側。両者で共有) と `V_out[5120,5120]` (w2 の出力側)。直交行列で、bf16 か FP8 | `B1, B3 [2304,5120]`、`B2 [5120,2304]` を EXL3 K4 で持つ。B2 には中間ニューロンの整列 (並べ替え) が要る |
| expert ごとに持つもの | `W_e·V` を EXL3 trellis で持つ。列 (固有方向) を分散の順に並べ、帯域ごとに K を変える (例: 先頭 256 列は K3、残りは K2)。suh / svh は今と同じ | `Δ_e = W_e − α_e·B` を EXL3 K2 で持つ。α_e はスカラー |
| manifest | ds41rt staged (`meta.ds41rt.schema`) を拡張し、`fold.basis` (テンソル名、dtype) と `bands[] = {col_start, col_end, bits}` を足す | `fold.base` と `alpha` を足す |
| 追加の容量 | bf16 なら 105MB/層 × 40 = **4.19GB (0.062 bpw)**、FP8 なら 2.1GB (0.031 bpw)【計算】 | K4 で 17.7MB/層 × 40 = **0.71GB (0.010 bpw)**【計算】 |
| 測った利得 | 理論上は 0.013〜0.044 bit。シミュレーションでは +0.001〜+0.010 bit | 0.0027 bit 以下 (残差比 0.9957〜0.9974 から 0.5·log2(1/ρ)) |
| **正味** | **−0.06〜−0.02 bit (損)** | **約 −0.008 bit (損)** |

### 3.2 推論カーネル (SM120 で base / 回転と expert GEMM を融合できるか)

- **TF-delta の w1 / w3**: y = Bx + Δ_e x になる。Bx はトークンごとに 1 回だけ密 GEMM で計算し、その層の 6 expert で共有できる。
  - ds41rt / exllamav3 の EXL3 MoE GEMM の epilogue で、事前に計算した Bx のタイルを、SwiGLU (clamp 10) の前に足せばよい。融合自体は**可能**である。C 入力を持つ epilogue は、mma.sync 系のカーネルなら素直に書ける【推測】。
- **TF-delta の w2**: Σ_e g_e (B2 + Δ2_e) h_e = B2 (Σ_e g_e h_e) + Σ_e g_e Δ2_e h_e である。
  - 結合後に密 GEMM を 1 回追加すれば済む。ただし、**中間ニューロンを expert 間で揃えないと B2 に意味が無い**。§2.2 E では、揃えても共有は見えなかった。
- **TF-fold**
  - 入力側: x' = V_inᵀ x を層ごとに 1 回計算し、w1 / w3 と 6 expert で共有する。EXL3 の入力側 128 Hadamard と suh は、そのまま残す。
  - 出力側: 結合した後に V_out を 1 回掛ける。
  - 帯域ごとの混合 K は、K 方向を分割した 2 回の EXL3 GEMM を同じアキュムレータに積む形で実装できる。いまの kernel は、1 テンソルの中で K が一様であることを前提にしている。そのため、ds41rt の `k23` / `k34` AOT パッケージ (`r2_ds41rt.md:85`) に、K 方向の帯域で分けた版を足す改修が要る【推測】。
- **速度の費用** (decode c1、1 ステップの読み出し量)【計算】
  - routed (K2、6 expert × 40 層) = 2.16GB
  - TF-fold の V を bf16 で持つと、4.19GB を余分に読む。routed の読み出しが約 3 倍になり、全体 (密層 FP8 7.2GB + head 1.32GB + routed) でも **+39%** になる。FP8 で持っても +20%。
  - TF-delta の base (K4) は +0.71GB で、c1 では routed の +33%、c16 では +2.5% 程度。
  - **品質の得が 0.01 bit なのに、速度は 2〜4 割落ちる。** 採る理由が無い。

### 3.3 VRAM 予算 (2 枚で約 150GB) での品質

| 構成 | 実効 bpw | 中身 | 品質の見込み |
|---|---|---|---|
| EXL3 K2 一律 (E3-0、いま作成中) | 2.035 (138.2GB、`r2_ds41rt.md:112`) | greedy beam16 | 0909 の値で KL 0.36【資料】 |
| EXL3 K2 一律 + Viterbi + refit (E3-1) | 2.035 | 同じ形式 | NLL 0.243 → 0.139 nats/token (0909)【資料、`r2_quant_tools` §5】 |
| **EXL3 K2/K3 混合 (expert ごと)** | 2.21 (150GB。experts の **17.3%** を K3)【計算】 | routing 頻度、感度、super expert で配分 | 2.41bpw の expert 別配分 + 校正で KLD 0.198 / 0.129 (0909)【資料】 |

### 3.4 変換手順 (仮に作る場合)

1. 層ごとに、`r3_fold_measure.py` の C 段で `V_in` と `V_out` を作る (192 expert の共分散の固有分解。CPU で 1 層約 3 分)。
2. 帯域と K を決める (列ごとの分散で逆注水し、VRAM 予算に合わせる)。
3. exllamav3 の `quantize_tiles` (Viterbi) で `W_e·V` を符号化する。
   - Hadamard は入力側 128 ブロックのまま使う。
   - 帯域ごとに K を変えるため、`quantize_experts_exl3_sm120.py` を、K 方向を分割して呼ぶ形に改修する。
4. staged manifest を書き、ds41rt の loader と kernel を改修する。
5. 合計で 2〜3 週かかる【推測】。

### 3.5 品質評価 (作る場合も、作らない場合も共通)

- 教師には `harness/stream_ref.py` の teacher-forced logits (top-32) を使う。`work/teacher/agent24*.jsonl` と `ja16.jsonl` がある。
- 区分は neutral / code / agentic / **日本語** の 4 つに分け、それぞれで KL と top-1 一致を出す。
- 先に層単位の proxy を測り、良さそうなものだけを全体の KL にかける。proxy は、stream_ref の ExpertStore を差し替えて測る 1 層ぶんの出力誤差 ||ΔY||/||Y|| とする。

## 5. 日本語への影響

| 方式 | 日本語への影響 | 根拠 |
|---|---|---|
| expert の統合・折りたたみ (M-SMoE、Sub-MoE、MoBE、REAP) | **悪くなりやすい。** 統合は routing 頻度で重み付けするのが普通で、校正データは英語とコードが中心である。日本語に特化した expert は、頻度が低い側として潰されやすい。§2 で expert どうしがほぼ直交していると分かったので、統合すると、その expert 固有の情報の 99% が失われる | 多言語 MoE では、前段と後段の層の routing が言語ごとに分かれ、中段は英語と揃う。多言語 expert に手を入れると性能が下がる (Bandarkar et al., [arXiv 2510.04694](https://arxiv.org/abs/2510.04694v1))。REAP は text だけで選ぶと vision が無作為より悪くなる (`r2_quant_tools.md` §4.1)【資料 + 推測】 |
| TF-fold (回転だけ) | 中立。直交変換なので、どの expert を残すかは変わらない。誤差がわずかに減るだけ | §2.2 F |
| EXL3 の混合精度 | **配分のしかたで、日本語を守ることも良くすることもできる** | 下の手順 |

**日本語を損なわない、または良くするための具体策** (Tensorfold の代わりに EXL3 の工程へ入れる)

1. **日本語で routing 頻度を集計する。** stream_ref の `STORE.counts` を `ja16.jsonl` と GLM の要求ログの日本語部分で取り、層 × expert の頻度 f_ja を出す。英語・コードの頻度 f_en と比べて、f_ja / f_en が大きい expert を「日本語 expert」とする。
2. **ビット配分の重要度に日本語の項を入れる。** 重要度 = 感度 × max(f_all, λ·f_ja) とする。λ は 2〜3 程度【推測】。さらに、層ごとに日本語の上位 5% の expert には K3 を下限として与える。150GB の予算で K3 にできる expert は 17.3% あるので、その一部をここに回す。
3. **校正データ (E3-2) に日本語を 20〜30% 入れる【推測】。** これで Hessian が日本語の活性の分布を反映する。
4. **評価では日本語の KL / top-1 と、日本語の QA を独立に監視する。** 合格線は「日本語の低下 ≤ 3 点」(`DECISION.md` §4.2 G1)。
5. **日本語を「向上させる」なら、QAD / 蒸留の段階で日本語の教師データを厚くするのが唯一の現実的な手段である。** 量子化や折りたたみは、元のモデルより良くはできない。量子化後の回復学習で、日本語の比重を元の学習より上げた場合に限り、日本語が向上する可能性がある【推測】。

## 7. 未解決の問い

1. **H で白色化した空間 (W·H^{1/2}) では、expert 間で共有されるものがあるか。** 重みの空間では無い (§2)。しかし活性が強く偏っているので、出力誤差の尺度では別の結果になる可能性がある。
   - 測り方: stream_ref の `moe_forward` に hook を入れ、層 3 / 20 / 37 の FFN 入力 x を 4k トークンぶん取る。H を推定し、§2 の C と F を H で重み付けしてやり直す。
2. 層 1 (Engram の直後) と、層 37 の e290 のような super expert の分布。今回の 3 層には、層 1 を入れていない。
3. ds41rt の staged manifest が、expert ごとの K2/K3 を本当に表せるか (粒度が tensor なのか expert なのか)。`v41_exl3.rs` を読んで確かめる必要がある。
4. TensorFold の dsv41 fork の transport を PCIe P2P に置き換えたときの all-gather の遅延。84 回 × 2 rank で、2ms/token の予算 (DESIGN §3) に収まるか。
5. greedy beam16 の relerr 0.377 は 0909 での値 (`build/qrecipe/tools/requant_probe.py:5`) である。1017 の出力 (`$MODELS/DeepSeek-V4.1-Flash-1017-EXL3-2.0bpw`) でも同じかどうかは、GPU で exllamav3 の reconstruct を使って確かめる必要がある。
