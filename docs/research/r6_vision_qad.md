# 画像を QAD とビット配分に組み込む設計 (r6、2026-10-18)

対象: DeepSeek-V4.1-Flash-1017 の EXL3 2.0bpw パック (v0、v1) と、これから作る QAD (L2 / L3) と K2/K3 混合 (v2)。
GPU は使っていない。CPU のコンテナ (`dsv41-quant:151`、`--network none`、GPU 割り当てなし) だけで測った。
凡例: 【実測】手元で測った値、【計算】式から出した値、【推測】根拠が間接的な値。

---

## 0. 要約

- **画像トークンはテキストとは別の専門家を通る。** 画像用の補正バイアス `bias_vl` は、テキスト用 `bias` とほぼ無相関である (40 層平均の Pearson −0.05、Spearman −0.32)。差の広がりは `bias` 自身の広がりの 1.69 倍ある【実測】。
- 層 0 の CPU 近似では、実画像 8 枚の routing の上位 96 専門家がテキストの上位 96 と 24 個しか重ならなかった。これは無作為に選んだときの期待値と同じである。画像の routing の 27% は、テキストで下位 30% の「冷たい」専門家に行く (テキストでは 7.6%)【実測、近似】。
- **リスク 1 (ビット配分)**: テキストの頻度だけで K3 を選ぶと、K3 はテキストの routing の約 60% を覆うが、画像は 19〜23% しか覆わない。画像で押し上げられる専門家が K3 に入る率は無作為の半分になる (1.9 / 19 個)【計算】。K は上がるだけなので v1 より悪くはならない。ただし改善はテキストに偏る。
- **リスク 2 (QAD)**: テキストだけの capture で suh/svh を学習すると、画像とテキストの両方が使う専門家の scale が、テキストの入力分布に合わせて動く。検証もテキストだけなので、画像で悪化しても採用されてしまう。**L2 にはこれを止める仕組みが無かった。**
- 改修 (CPU テストは新規 48 件と既存 41 / 49 / 26 件がすべて通過):
  - `capture_moe.py` は画像付きの系列を記録できる。token_types を field `tt` として保存し、画像トークンを多めに残す (`--img-boost`)。tools/vl/build_sets.py の `vl_calib.jsonl` もそのまま読める。
  - `qad_l2.py` に画像トークンの損失重み (`--img-weight`) と「画像の守り」(`--img-guard-tol`) を足した。守りは、画像だけの検証誤差が v1 より悪くなる expert を採らない。
  - 新規 `vl_rows.py` は画像付きの行形式を作り、検査し、画像を読み込む。
  - 画像の無い入力では、保存形式・指紋・学習結果がビット単位で従来と同じである。
- 提案:
  - ビット配分の重み: `code 0.25 / 英語・agent 0.25 / ja 0.30 / img 0.20`。img の頻度は教師の画像トークン routing (`counts_vl`) から取る。
  - 合格基準: H-VL1〜4 と R-VL1〜4 (§5)。画像 KL が v1 比 +1% 以内、ds41rt の画像正答率が v1 比 −1pt 以内、など。

## 1. 前提: 画像の経路で量子化が効く所と効かない所

| 部分 | 量子化 | 画像トークンへの効き方 | 出典 |
|---|---|---|---|
| ViT 32 層 + aligner | BF16 原重みのまま (全版) | 変化なし | `arch_spec.md` §ViT、`ref/vision.py` |
| 区切り埋め込み (start / end / newline) | BF16 のまま | 変化なし | `model.py:1222-1225` |
| Engram | FP8 のまま | 画像位置は DEAD (引かない、ゲート 0) | `model.py:1252-1255`, `engram.py:166` |
| attention、shared expert | 原本と同じ (FP8) | 変化なし | — |
| **routed experts (40 層 × 384)** | **EXL3 K2 (v0、v1)、K2/K3 (v2)、suh/svh 学習 (L2)** | **画像区間の全位置 (START/END/NEWLINE を含む) が通る。gate は `bias_vl` で選ぶ** | `model.py:811-830` |
| DSpark (mtp 3 層) | — | 画像区間を見ない (生成側だけ)。`mtp.N.ffn.gate.bias_vl` は `bias` と同一 | §2.1 |

- ds41rt も router カーネルで `image_mask ? bias_vl : bias` を使う (`ext/ds41rt/native/cuda/kernels/v41_router.cu:83`)。したがって §2 の routing の違いは運用でも出る。
- ds41rt の画像 API は OpenAI 形式の `image_url` を受ける。data: URL か http(s) が使え、1 要求 16 枚まで、1 枚 32MB、合計 64MB である (`rust/crates/ds41rt-api/src/native_v41/images.rs:16-37`)。
  - 当初は HTTP で 1 回確かめる予定だった。作業中に ds41rt が止まって `dsv41-qad-jaklT` (jakl32 の教師、GPU0) に替わったため、確認はソースで行った。
- 画像の性能に効く量子化は routed experts だけである。そこで本書は、画像トークンがどの専門家を通るか、そしてそこに配分と QAD がどう効くかを扱う。

## 2. 分析 (課題 1): bias_vl はテキストとどれだけ違うか

ツール:
- `tools/r6_vl_bias.py`: 原重みの `layers.N.ffn.gate.{bias,bias_vl}` を読み、`work/teacher/{agent24,ja16}_teacher.pt` の counts と突き合わせる。出力は `work/r6/r6_vl_bias.json`。
- `tools/r6_vl_proxy0.py`: 層 0 の CPU 近似。出力は `work/r6/r6_vl_proxy0.json`。
- `tools/r6_make_images.py`: 合成画像と、配布条件の明らかな写真を用意する。出力は `work/r6/img/`。

topk は bias 全体に定数を足しても変わらない。そこで差は中央値を引いた `dc = (bias_vl − bias) − median` で見る。

### 2.1 bias と bias_vl の差の分布 (40 層)【実測】

| 指標 | 40 層平均 | 範囲 | 読み方 |
|---|---|---|---|
| sd(dc) / sd(bias) | 1.69 | 0.70 (層 23) 〜 3.22 (層 0) | 1 を超えるので、画像の補正はテキストの補正より大きく動く |
| 層 0〜12 の sd(dc)/sd(bias) | — | 1.87〜3.22 | 浅い層ほど違う |
| Pearson(bias, bias_vl) | −0.05 | −0.46 (層 1) 〜 +0.76 (層 23) | ほぼ無相関。層 19、23、29、34、36 だけ正 (0.36〜0.76) |
| Spearman(bias, bias_vl) | −0.32 | — | 順位ではやや逆向き。テキストで押し上げる専門家ほど画像では押し下げる傾向 |
| z ≥ 2 の押し上げ / z ≤ −2 の押し下げ (本数/層) | 15.9 / 3.9 | 層 30〜39 は押し下げ 0〜3 | 右に裾が長い。少数の専門家を画像のために大きく持ち上げている |
| mtp 0〜2 | bias = bias_vl (差 0、ばらつき 0) | — | DSpark は画像の区別を持たない (arch_spec の記述と一致) |

### 2.2 画像候補 (bias_vl で選ばれやすくなる専門家) とテキストの頻度の重なり【実測】

画像候補は、層ごとに dc の上位 5% (19 個) とした。全層の一覧は付録 A に載せた。テキストの頻度は `r3_routing_skew_measured.md` と同じ agent24 / ja16 の教師の counts を使った。

| 指標 (40 層平均) | agent24 | ja16 | 無作為なら |
|---|---|---|---|
| 候補 19 個のうちテキスト上位 96 に入る数 | 3.15 | 3.08 | 4.75 |
| 候補 19 個のうちテキスト下位 115 に入る数 | 7.13 | 6.38 | 5.69 |
| 候補 19 個が持つテキストの routing の割合 | 3.1% | 3.2% | 4.9% |
| 候補の agent 順位の四分位 (1 = 最も熱い) | 127 / 221 / 318 | — | 96 / 192 / 288 |
| Spearman(dc, log テキスト頻度) | −0.10 | −0.01 | 0 |

- **画像候補は、テキストでは冷たい側に寄っている。** 候補の 37.5% がテキストの下位 30% に入り、上位 25% に入るのは 16.6% だけである。
- 深い層 (36、39) の押し下げ候補 (dc の下位 19 個) は、テキストの最も熱い専門家を含む (層 36 の e313、層 39 の e91 はどちらも agent で 1 位)。押し下げ候補 19 個がテキストの routing の 11.5〜12.0% を持つ。画像はテキストの主力から外されている。
- 日本語 (ja16) でも傾向は同じで、日本語専門家と画像候補の特別な重なりは見えなかった。

### 2.3 層 0 の CPU 近似: 実際の画像は routing でどこへ行くか【実測、近似】

bias だけでは、画像が実際にどこへ行くかは決まらない (raw score による)。そこで層 0 だけを CPU で近似した。

- **近似の中身**: 層 0 の MoE 入力を `ffn_norm(埋め込み)` とし、attention の寄与を落とした。hyper-connection の 4 複製は同じ向きのまま保たれるので、RMSNorm の後はこの形になる (`model.py:959-996`)。
- **画像側**: ViT 32 層と aligner を BF16 原重みから fp32 で実行した。前処理は `ref/image_processor.py` の `load_image` そのままである。
- **画像**: 8 枚、計 4,048 画像トークン。
  - 写真 3 枚: モデル同梱の carrots / corn (MIT)、matplotlib 同梱の grace_hopper (パブリックドメイン)。
  - 自作の画面 5 枚: 日本語文書、コード、グラフ、表、3000×2000 の UI。実トラフィックが PNG の画面写し型 (§7) なので、それに寄せた。
- **近似の妥当性 (テキストで検証)**: テキストの近似と実測 counts (層 0) を比べた。cos 0.43 / 0.41、Spearman 0.35 / 0.40 (agent / ja)、上位 96 の重なり 44 / 41 個 (無作為なら 24) だった。近似は分布を実際より尖らせる (Gini 0.65、実測 0.45)。**向きを見る程度には使えるが、値はそのまま使えない。**

| 指標 (層 0、近似) | 結果 |
|---|---|
| 画像の routing の偏り | 上位 25% で 87%、Gini 0.80 (テキストの近似は 0.65) |
| 画像とテキスト (実測) の分布の cos | 0.25 (agent)、0.22 (ja)。テキストどうしは 0.86 |
| 画像の上位 96 とテキストの上位 96 の重なり | 24 / 96 (無作為の期待値と同じ) |
| 画像の routing のうちテキストの下位 115 へ行く割合 | **27.0%** (テキスト自身は 7.6%) |
| 画像候補 19 個 (§2.2) が受ける画像の routing | **14.0%** (一様なら 4.9%)。テキスト用 bias で選ばせると 1.0% |
| 押し下げ候補 19 個が受ける画像の routing | 2.6%。テキスト用 bias だと 9.7% |
| bias_vl とテキスト用 bias で選んだ画像の routing の cos | 0.83 |

- bias_vl が押し上げた専門家は、画像が実際に使う専門家である。テキストの bias のままなら、画像は押し下げ候補に集まる。少なくとも層 0 では「bias_vl で選ばれやすくなる = 画像特化候補」という読みが成り立つ。
- 層 1〜39 は attention の寄与が大きく、この近似は使えない。実測は GPU の段で `counts_vl` (§3.1) から取る。

### 2.4 画像特化候補が K2 のまま冷遇されるリスク【計算】

SPEC §2.3 の配分 (層内で重要度の上位 19.3% を K3、一様分布との混合 m = 0.3) を、テキストの頻度だけで作った場合を試算した。

| K3 が覆う routing の割合 | agent | ja | 画像 |
|---|---|---|---|
| 40 層平均、テキストだけで配分 (agent 0.7、ja 0.3) | 61.5% | 59.7% | 一様と仮定すると 19.3%。画像候補 19 個のうち K3 に入るのは 1.9 個 (無作為なら 3.7 個) |
| 層 0 近似、テキストだけで配分 | 47.2% | 48.3% | 22.7% |
| 層 0 近似、画像を入れて配分 (agent 0.5、ja 0.3、img 0.2) | 43.6% | 46.6% | **60.2%** |

評価:

1. **K2/K3 混合 (v2)**
   - テキストだけで配分すると、画像は K3 の恩恵をテキストの 1/3〜1/2 しか受けない。K は上がるだけなので、v1 より悪くなることは無い。
   - 画像を 0.2 入れると、層 0 では画像の被覆が 23% から 60% に上がる。代わりに agent が 3.6pt、ja が 1.7pt 下がる。
   - ただし画像の routing がほぼ一様なら (学習時の負荷分散 `noaux_tc_for_vl` が効いている場合)、配分では画像を守れない。その場合、画像を守る手段は QAD の守り (§3.2) になる。
2. **L2 (suh/svh の局所蒸留)**
   - 画像特化かつテキストで冷たい専門家は、テキストの capture では行数が `--min-tokens 256` に届かず cold になり、v1 のままになる。こちらは安全側である。
   - 危ないのは、画像とテキストの両方が使う専門家である。scale がテキストの入力分布に合わせて動き、テキストの検証だけで採用される。
   - 画像の入力 (aligner 出力) はテキストの埋め込みとは分布が違う。L2 は入力の各次元の scale (suh) を直接動かすので、テキストで大きくない次元を画像が使っている場合、そこが崩れうる【推測】。
3. **L3 (全体 KL)**: 教師の系列がテキストだけなので、L2 と同じリスクがある。L3 に進むなら、画像の教師 (vl_kl) も `--teacher` に入れる必要がある (qad_l3 は未改修、§6)。
4. **v1 自体**: v0→v1 の再符号化は全 expert に一律に掛かった。画像の性能はまだ一度も測っていない。**最初に v1 の画像基準を取る** (§6 の G1)。

## 3. 改修 (課題 2、3)

既存の動作は変えていない。画像の無い入力では、保存形式 (row_bytes 10290)、capture の指紋、sampling、L2 の学習結果がビット単位で一致する。これは CPU テストで確認した。

### 3.1 `harness/capture_moe.py` (画像系列の記録)

| 項目 | 内容 |
|---|---|
| 入力 | `vl_rows.py` の行 (`ids` + `images: [{path, start, grid, sha256}]`) と、tools/vl/build_sets.py の行 (`vl_ids` / `token_types` / `image_spans`) の両方。後者は `vl_rows.normalize_row` で変換し、token_types が再構成と一致するかを照合する |
| forward | 画像付きの行だけ `model.forward(ids, 0, images=[ImageInput...], token_types=tt)` を呼ぶ。区間は bias_vl で routing され、Engram は DEAD になる。テキストの行は従来どおり |
| 画像の印 | **flags の 8 bit はすべて使用済み (F_DUP = 128) なので、flags には入れていない。** 既存の F_* の値は変えず、新しい field `tt` (int8、token_types そのもの、−1 = テキスト) を足した。field は画像付きの記録 (`meta.vl = true`) だけが持つ。row_bytes は 10291 |
| 間引き | `--img-boost` (既定 2.0) で画像トークンの保持率を p × 2 にする。kp に入るので、学習側では 1/kp で自然な分布に戻る |
| 統計 | bucket `tok_img` (cnt / wsum / xsq [L, E]) を足した。画像トークンだけの routing 統計で、ビット配分の img 頻度に使える |
| 重複除外 | 画像区間の ids は全部 129264 なので、接頭辞ハッシュに画像の sha256 (無ければ path) を混ぜる。ids が同じでも画像が違えば重複扱いしない。テキスト位置のハッシュ値は従来と同じ |
| 言語タグ | 画像の位置は kana / han / ja / zh のビットを持たない (special は残す) |
| その他 | 画像区間が `--max-seq-len` を超える行は切らずに飛ばす (`skipped_image_overflow`)。images の無い行に 129264 があれば止める。`verify` は画像行を bias_vl で再計算する (`load_real_gate` が bias_vl も読む)。画像なしの part と混ぜて読むと tt = −1 で埋める。`pack` も tt を含む |

### 3.2 `harness/qad_l2.py` (画像トークンの重みと守り)

| 引数 | 既定 | 内容 |
|---|---|---|
| `--img-weight` | 1.0 | 画像トークンの損失の重み `c_t = imp × (ja_weight if 日本語) × (img_weight if 画像)`。**推奨は 1.5**。画像の無い記録には効かないので、既定は従来と同じ値にした |
| `--img-guard-tol` | 0.0 | 画像の守り (expert mode)。検証に画像の対が `--min-val-img` (既定 32) 以上ある expert で、学習後の画像だけの検証誤差が v1 の (1 + tol) 倍を超えたら `rejected_img` (v1 のまま)。layer mode では層全体で同じ判定をする |
| (自動) | — | 検証の分割では、画像を含む系列を 3 つ目の層として選ぶ。`layer_val` に `img` / `text` を足す (画像があるときだけ) |

- 合成データでの効き【実測、test_vl_capture_qad】:
  - 画像の重みを 1→4 にすると、画像の層出力の誤差は 0.0393→0.0318、テキストは 0.0550→0.0561 になった。日本語の重み (0.2306→0.2302) より効きが大きい。これは画像の入力分布をわざと変えてあるためである。
  - 合成データでは、守り (tol 0) で落ちた expert は無かった。教師が単一なので悪化が起きない。tol −1 で全件を落とし、守りが正しく掛かることだけ確かめた。

### 3.3 `harness/vl_rows.py` (新規)

- 行形式 `dsv41.vl-row.v1` の作成 (`build`: 公式 encoding.py + image_processor.plan_image_grid) と検査 (`check`)。
- 画像の読み込み (`image_inputs`: grid と sha256 を照合) と、区間の補助関数 (`row_token_types`, `image_salt`, `row_digest`, `normalize_row`)。
- 作った行は、公式 `generate.prepare_case` と ids、token_types、patches が一致する【実測】。

**注意 (作業中の事故)**: 並行していたエージェントの `harness/stream_ref_vl.py` (教師 / 学生の画像対応。`test_stream_ref_vl.py` と組) を、存在を知らずに新規作成のつもりで上書きした。元の内容は失われた (git なし、写しなし)。

- 自分の版は `vl_rows.py` に移し、`stream_ref_vl.py` は消した。メインの会話には通知済みである。

## 4. ビット配分に画像を入れる提案 (課題 4)

**重要度** (SPEC §2.3 の式に img を足す):

```
I[l,e] = α_l × Σ_d π_d × S̃_d[l,e],   S̃_d = (1−m)·S_d + m/384 (m = 0.3)
π = {code 0.25, other 0.25 (英語の推論・agent・ツール JSON), ja 0.30, img 0.20}
```

- 日本語 0.30 は据え置く。テキストの英語側 (code + other) を 0.70 から 0.50 に減らし、その分を img に回す。ユーザーの要件 (日本語、中国語混入抑制、画像) のうち、日本語を削らない形にした。
- `S_img` は、画像の教師 (vl_kl、§6 G1) の画像トークンだけの routing 回数 (`counts_vl`) から作る。重み付けは xsq (capture の `xsq.tok_img`) が使えればそちらを使う。
- テキストの区分 (code / other / ja) は `counts − counts_vl` を使う。テキストの頻度に画像が混ざらないようにするためである。
- `routing_stats.v1` に `per_domain.img` を足す。`domains.img.tokens` は画像トークン数で、区切りの START/END/NEWLINE を含む。

**π_img は、実測した画像の偏りで決める**:

| `counts_vl` の層平均 Gini | π_img | 理由 |
|---|---|---|
| 0.5 以上 (層 0 の近似は 0.80) | 0.20 | 画像の熱い専門家を K3 にすれば、画像の被覆が大きく上がる (層 0 近似で 23%→60%、テキストの代償は −2〜4pt) |
| 0.3〜0.5 | 0.10 | 効きが中程度 |
| 0.3 未満 (ほぼ一様) | 0.05 | 配分では画像を守れない。§3.2 の守りと §5 の基準で守る |

**保護枠** (日本語 expert と同じ形):
- 層内で share_img が上位 5% かつ share_img / share_text ≥ 2 の expert を「画像 expert」として K3 に固定する。
- 枠全体の 15% を上限とする (日本語は 25%)。合わせて 40% が保護枠で、残り 60% を重要度順に配る。

**速度**:
- 画像トークンは prefill にしか出ない。`decode_weighted_K ≤ 2.45` の判定は、テキストの decode の routing (img を除く) で行う。
- 画像 expert を K3 にすると、K3 枠 (VRAM) は使うが、decode の速度はほとんど変わらない。
- 画像付き要求の prefill は、画像 expert の分だけ遅くなりうる。R-VL3 で見る。

**作り方** (`tools/mixk_plan.py` は未実装。SPEC §2.3 の新規ツール): `π` に img を足すのと保護枠の 2 点を加える。今回の試算 (`r6_vl_bias.py` の `k3_cover`) は層内の簡易版である。

## 5. 合格基準に画像を足す提案 (課題 5。QAD_PLAN §5 への追加案)

比較は v1 との対で行う。画像の評価集合は tools/vl/build_sets.py の `work/vl/vl_kl.jsonl` (教師 KL 用、日本語が半分以上) と `work/vl/vl_gen.jsonl` (ds41rt 生成評価、`tools/vl_eval.py`) を想定した。

**ハーネスの段 (H、§5 の H1〜H5 に加えて全部満たす)**

| ID | 指標 | 基準 |
|---|---|---|
| H-VL1 | 画像系列 (vl_kl) の回答トークンの KL (教師 top-32) | 点推定で v1 比 +1% 以内。かつ系列 bootstrap の 95% 区間の下端が 0 を超えない (有意な悪化が無い) |
| H-VL2 | 同じく top-1 一致 | v1 から −0.3pt より下がらない |
| H-VL3 | vl_kl のうち日本語の問い | KL が v1 比 +2% 以内。日本語の回答本文の zh_only の質量 (QUALITY.md の方法) が v1 より増えない |
| H-VL4 | L2 の層ごとの報告 `layer_val.img` | 40 層中 38 層以上で `qad ≤ v1`。`rejected_img` の合計が accepted の 10% を超えたら、`--img-weight` を 1.5→2.0 にして再実行するかを判断する |

**ds41rt の段 (R、§5 の R0〜R5 に加えて)**

| ID | 基準 |
|---|---|
| R-VL1 | `vl_gen` の正答率が全体で v1 比 −1pt 以内。区分 (vqa / ocr / chart / doc / screenshot / 日本語 vqa) ごとには −3pt 以内 |
| R-VL2 | 日本語の画像問の回答で、日本語で答える率が 99% 以上、zh_only の字の出現が v1 より増えない (`vl_eval.py` が数える) |
| R-VL3 | 画像付き要求 (1024×768 を 1 枚と 3000×2000 を 1 枚) の prefill 時間が v1 の ±5% 以内 (v2 の K3 混合で効く) |
| R-VL4 | 人手で画像 10 問 (画面写し 6、写真 4) を v1 と並べ、明らかに悪い回答が無い |

- **−1pt を判定できる問題数**【計算】: 対にした正誤の差の標準誤差は、不一致率を d として √(d / n) である。d = 0.10、n = 1,000 で 1.0pt になり、−1pt はちょうど 1 標準誤差に当たる。そこで R-VL1 は「点推定 −1pt 以内、かつ対の bootstrap の 95% 区間の下端が −3pt より上」と読む。vl_gen は 1,000 問以上を勧める。
- v2 (K3 混合) にも同じ基準を使う。v2 では画像 KL が下がることを期待するが、基準は「悪化しない」にとどめる。
