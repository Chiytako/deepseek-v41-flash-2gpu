# R5: 配信時に中国語 (簡体字) の混入を抑える仕組み (ds41rt / vLLM)

作成日: 2026-10-18
対象: `DeepSeek-V4.1-Flash-1017` を ds41rt (0-spark、EXL3 pack v0) と、A/B 用の vLLM + vllm-exl3 (r4_vllm_ab.md) で配信する構成。
前提資料: `SPEC_QUANT_JA.md`、`r3_japanese.md` (§2.3 の簡体字混入の基準値、G-JA6)、`results/QUALITY.md`、`r2_ds41rt.md` (§6〜7)、`r3_qad.md`、`r4_vllm_ab.md`。
凡例: 【実測】はこの調査で手元で確かめた値、【資料】はコードや文書の記載、【計算】は式から出した値、【推測】は根拠が間接的な値。
GPU は使っていない。稼働中のコンテナとサーバーには触れていない (要求も送っていない)。取得したデータは無い (手元の語彙、コーパス、保存済みの教師 logits だけを使った)。

この調査で作ったもの

- `tools/zh_serve_mask.py`: 語彙の分類 (Z1 / バイト片 / T2)、中国語コーパスでの捕捉率、日本語コーパスと GLM 実トラフィックでの出現数、ds41rt 形式の許可マスクの書き出し。CPU で約 13 秒。
- `tools/zh_teacher_mass.py`: 保存済みの teacher-forced top-32 (`work/teacher/{ja16,agent24}_{teacher,v0}.pt`) を torch 無しで読み、回答部分で V4.1 が Z1 に置く確率を、1017 原重みと v0 で比べる。
- `tools/zh_regex.py`: ds41rt の既存機能 (`response_format: {"type":"regex"}`) だけで回答部分の簡体字専用字を禁じる正規表現。コード変更なしの評価用。
- 出力: `work/zh/serve/` (`summary.json`、`teacher_mass.json`、`z1_ids.json` 13,029 個、`t2_ids.json`、`allow_mask_z1.u32` 16,160 バイト、`answer_regex.txt`、`example_request.json`)。
- 実行は `tools/.venv/bin/python -I <script>`。

## 0. 結論

1. **量子化版 (v0) は、原重みより約 11〜15 倍多く簡体字専用トークンに確率を置く。** temperature 1.0 では日本語回答の 3.5〜4.5% に 1 字以上の混入が起きる見込みで、G-JA6 (1% 以下) を超える (§1.2)。
   - 回答の自由文で、1,000 トークンあたりの Z1 の確率質量は、原重みが 0.0075〜0.0078、v0 が 0.086〜0.110 だった【実測、top-32 の下限】。
   - 混入しかける位置では、ほとんどの場合、日本語の字体が top-1 にある (约→約、英语→英語、头→頭、职场→職)。**マスクすれば、モデルはほぼ常に日本語の同じ語を選ぶ。** マスクは品質を下げる手段ではなく、量子化で増えた誤りを 1 種類取り除く手段である。
2. **抑制の本体は「回答部分 (思考の後) だけで、簡体字専用字を含むトークン (Z1、13,029 個) の logit を -inf にする」硬いマスクにする。** 柔らかい bias と、語単位の禁止 (T2) は採らない (§5.1)。
   - Z1 は日本語コーパス 409 万トークンで 21 回 (すべて ja.wikipedia の中国地名の引用) しか出ない【実測】。誤抑制はほぼ起きない。
   - 簡体字の文の 97.3% は Z1 トークンを 1 個以上含む。中国語への切り替わりの多くは、最初の 2〜3 トークンで止まる【実測】。
   - T2 (日本語の字だけで書ける中国語の語のトークン、4,099 個) は、GLM の日本語回答の 2.2% で正しく使われていた (列入 = 配列入力、不均 = 不均一、的主 = 的主張、不等 = 不等式)。硬く禁じてはいけない。
3. **ds41rt は logit_bias / bad_words / logits processor を持たない。ただし、要求ごとの語彙ビットマスクを、目標の検証・GPU サンプラー・DSpark の提案の切り詰めまで一貫して通す仕組みが、XGrammar 用にすでにある (§2)。** 言語マスクはこの「文法の状態 (`constraints::State`)」に 1 層足すだけで入る。
   - 改修は Rust 約 400 行で、CUDA の変更は無い (段階 1、§3)。
   - 送られた `logit_bias` は黙って無視される。効いているつもりにならないよう注意する。
4. **DSpark との整合は、目標側のマスクを正とし、提案は同じ状態機械で切り詰めることで取る。** ds41rt は sample-and-match なので、マスクで禁じたトークンの提案は必ず棄却される。切り詰めは受理率を変えず、検証の無駄だけを省く (§3.4)。
   - ドラフト側にマスクを入れる (CUDA 改修) 利点はほぼ無い。原重みでも v0 でも、回答の約 1 万位置で argmax が Z1 になった位置は 0 だった【実測】。
   - 受理率を崩すのは逆向きの不一致、つまり「ドラフトだけ禁じて目標は禁じない」場合と、「思考の範囲の判定が両者で違う」場合である。設計上これを起こさない。
5. **vLLM では `logit_bias` と自作の logits processor が投機デコードと併用できない (起動時または要求時にエラー)。** `bad_words` は上限 128 語、`allowed_token_ids` は思考の部分まで効いてしまう。使える経路は、reasoning-aware な structured outputs (xgrammar の文字クラス文法) である (§4)。
6. **性能への影響は小さい。** c1 では測れないほど小さく、c16 では段階 1 のホスト側コピーで round あたり約 0.5〜1 ms (1% 前後) かかる見込み【計算】。超えるようなら段階 2 (GPU 常駐の言語マスクとフラグ) で 0 に近づける (§6)。
7. **すぐできること (コード変更なし):** ツール無しの評価では、`response_format: {"type":"regex","regex": <answer_regex.txt>}` を付ければ、今の ds41rt で回答の簡体字を禁じられる (§3.6)。日本語評価セット (ELYZA-tasks-100、MT-Bench、MGSM ja) でマスクの有無の A/B を取り、品質が落ちないことを先に確かめる。
8. 拒否・安全挙動の変更 (無検閲化) は範囲外である (§8)。

  - 繁体字と日本の旧字体は入らない。

## 2. ds41rt の現状 (コード確認)

対象は配信経路の `serve-native` (`rust/crates/ds41rt-daemon/src/v41_native_serve/`、API は `rust/crates/ds41rt-api/src/native_v41.rs`)。

| 機能 | 対応 | 根拠 |
|---|---|---|
| `logit_bias` | **無し** (送っても無視) | `NativeRequest` (`native_v41.rs:55-64`) は prompt、constraint、images、max_tokens、sampling、events だけを持つ。sampling は `request_target_sampling` (`:162-200`) が temperature / top_p / top_k / min_p / seed だけを読む。API crate の注記に「`logit_bias`、`min_tokens` の logits-processor の面を持たない」とある (`tests/upstream_sampler.rs:8-9`)。未知のフィールドは無視される (r2_ds41rt §7) |
| bad words / 任意の logits processor | 無し | 同上。GPU サンプラーは mask → temperature → min_p → top_k → top_p の順で固定 (`README.md` の sampling 節) |
| 文法制約 (XGrammar) | **あり** (JSON schema、json_object、regex、ツールの DSML、思考の包み) | API: `native_v41/constraints.rs:8-45` が structural tag を組む。思考モードでは `sequence[any_tokens(exclude 128822), token 128822, content]` で、文法を `</think>` の後だけに効かせる (`:40-44`)。daemon: `v41_native_serve/constraints.rs` |
| 要求ごとの語彙マスクの経路 | **あり** (文法用) | 下の表 |

文法マスクの経路 (言語マスクもここを通せる)

| 段 | 何をするか | 場所 |
|---|---|---|
| 受付 | 要求ごとに matcher を作る。prefill 後の最初のトークン (anchor) もマスク付きで選ぶ | `scheduler.rs:325`、`:378-380` |
| ドラフトの切り詰め | DSpark の提案を、文法が拒む最初のトークンの手前で切る。停止トークンの提案は検証しない | `constraints.rs:84-93` (`truncate_proposal`)、呼び出しは `scheduler/independent.rs:93` |
| 検証のマスク | 仮の接頭辞 (提案) に沿って matcher を fork し、行ごとのマスクを作る。不要な行は `None` | `constraints.rs:128-139` (`prepare_verification_masks`)、`build_sampling_round` (`scheduler.rs:958-993`) |
| GPU サンプラー | 行ごとのマスク (`ceil(129280/32)` = 4,040 語、16,160 B) を pinned から H2D し、K1/K2/K5 が最初の述語として使う。マスク行だけを転送する | `v41_target_head.rs:491-565` (`upload`)、`native/cuda/kernels/v41_sampling_gpu.cu:113-132` (`row_allowed`) |
| CPU の代替経路 | 同じマスクで argmax / 標本化する | `scores.rs:407-421`、`constraints.rs:159-180` (`select_verification_sampled`) |
| 受理の判定 | sample-and-match: 提案が目標の (マスク後の) 標本と一致する間だけ受理し、最初の不一致では目標の標本を出す | `scheduler.rs:1567-1592` → `ds41rt_core::verify_dspark_greedy` |
| 確定 | 出したトークンで matcher を進める | `scheduler.rs:90-92` (`emit_one`) |
| 接頭辞キャッシュ | 保持した生 logits を、今の文法で選び直す。保持時の検算もマスク付き | `scores.rs` 冒頭、`scheduler.rs:1655-1662` |

- **制約付きの要求は、greedy の「compact」経路 (id だけをダウンロード) を使わない** (`independent.rs:117-121`)。マスクを付けると、temperature 未指定 (= greedy) の要求も GPU サンプラー経路に移る。
- ユーザーのトラフィックの 91.8% は tools 付きである (r3_japanese §2.2)。`tool_decoding_assistance` は既定で true (`native_v41.rs:203-207`) なので、**大半の要求はすでに文法の State を持っている**。ただし自由文の行は `fill_bitmask` が false を返し、マスク無しで流れている。
- DSpark のドラフトは、temperature 0 の argmax をグラフの中で取る (`speculative.rs:518, 616` で温度 0 を渡す)。カーネルは `shared + bias` の argmax である (`v41_dspark.cu:241-275`、位置ごとに `terminal.rs:292` で起動)。語彙マスクの入力は無い。

## 3. ds41rt への実装 (決定)

### 3.1 方針

- **言語マスクは文法と独立した「静的な拒否マスク + 位相の状態機械」として、`constraints::State` に合成する。** 文法がある要求では、両方のマスクの AND を取る。
- これで受付 (anchor)、ドラフトの切り詰め、検証マスク、GPU / CPU サンプラー、接頭辞キャッシュの選び直しが、すべて 1 か所の論理を通る。どこか 1 経路だけマスクが抜ける、という不整合が構造上起きない。
- 採らなかった案
  - XGrammar の structural tag に Z1 の除外を書く案: `any_tokens` は `exclude_tokens` を持つ (`native_v41/constraints.rs:42` で使用中)。ただし、ツール要求の自由文 (`triggered_tags` の外側の文) には除外を書く場所が無い。DSML 内だけ解除する、といった位相の切り替えも表せない。ツールの無い要求の評価に使う (§3.6)。
  - サンプラーに加算 bias を実装する案: GPU の K1〜K5 と CPU のサンプラーすべての logits 読み出しを変える必要がある。しかも §5.1 のとおり、柔らかい bias は要らない。

### 3.2 位相の状態機械 (要求ごと、ホスト側、Copy な小さい構造体)

| 位相 | 入る条件 | マスク |
|---|---|---|
| Think | 思考モードで開始したとき (prompt の末尾が `<think>`) | 無し |
| Free | prompt の末尾が `</think>` (128822)、または Think 中に 128822 を出したとき | **Z1 を禁止** |
| Fence | Free 中に ```` ``` ```` を奇数個含むトークン (前計算の表) | 文脈の Z1 が 20 個未満なら禁止、20 個以上 (中国語のコードを扱っている) なら解除 |
| Tool | Free / Fence 中に `｜DSML｜` (128825) を出したとき。以後は終わりまで | 解除 (ファイルの中身や引数に中国語が要ることがある) |

- 検証の行ごとのマスクは、文法と同じく仮の接頭辞 (提案のトークン列) に沿って位相を進めて決める。状態は値の複製で fork できる。
- `accept(token)` (確定) で、文法と位相の両方を進める。安全のため、Free で Z1 が確定したら `ensure!` で落とす (起きないはずの不変条件)。

### 3.3 改修箇所と量 (段階 1: CUDA 変更なし)【推測、行数は見積もり】

| ファイル | 変更 | 行数 |

### 3.4 DSpark (投機デコード) との整合

- **目標側のマスクが正である。** 出すトークンは常に、目標がマスク後の分布から引いたものになる (`scheduler.rs:1567-1592` の sample-and-match)。したがって出力の分布は「マスク後の目標の分布」と厳密に一致し、ドラフトに何を出させても偏らない。
- **提案の切り詰め (段階 1) は受理率を変えない。** Free の位相で提案に Z1 が入ると、その位置の目標の標本は決して Z1 にならないので、必ず不一致になる。その位置より後の提案は、どのみち捨てられる。手前で切っても受理数は同じで、検証の行 (GPU 時間とマスク転送) だけが減る。文法の切り詰め (`truncate_proposal`) と同じ論理である。
- **ドラフト側のマスク (段階 2、任意) で増える受理はほぼ 0 である。** ドラフトは greedy (温度 0) で動く。原重みでも v0 でも、回答の 9,935 位置で argmax が Z1 になった位置は 0 だった【実測、§1.2】。入れる場合の改修は約 40 行である。
  - `draft_step_tiles` (`v41_dspark.cu:241`) の `value = shared + bias` の直後に `if (lang_on[row] && !allow(col)) value = -inf` を足す。
  - `lang_on` は温度と同じ staging で H2D する (`terminal.rs` の `stage_sampling` / `upload_sampling_on`)。許可マスクは起動時に 1 回だけ転送する。
- **受理率を崩すのは逆向きの不一致である。**
  - ドラフトだけを禁じて目標は禁じない場合: 目標が Z1 を引いた位置で必ず外れる。しかも出力に中国語が残る。
  - 位相の判定が両者で違う場合: 例えば思考の中でドラフトだけを禁じると、目標が選ぶトークンをドラフトが提案できなくなる。
  - 段階 1 は位相を目標側の 1 つの状態機械で決め、ドラフトはそれで切るだけなので、どちらも起きない。
- **目標側のマスクは受理率をわずかに上げる。** v0 は「約」の位置で 约 に 2% を置く。マスクが無いと、temperature 1 でドラフト (約) と目標の標本 (约) がずれることがある。マスクするとこのずれが消える。

### 3.5 段階 2 (性能が足りないときだけ)

- GPU に常駐する言語許可マスク (16 KB、起動時に 1 回 H2D) と、行のフラグ `DS41RT_V41_SAMPLER_FLAG_LANG` を足す。
  - `row_allowed` (`v41_sampling_gpu.cu:113-132`) を `(文法マスクが無い || 文法ビット) && (!LANG || lang_allow ビット)` に変える。K1〜K5 はすべてこの関数を通るので、変更は 1 か所で済む。
- ホスト側では、「言語だけの行」をマスク arena に載せず、フラグだけを立てる。
- 改修: CUDA 30 行、ヘッダと FFI 40 行、`v41_target_head.rs` 40 行、計画の組み立て 30 行。native の再ビルドが要る。

### 3.6 コード変更なしの評価経路 (今すぐ使える)

- ds41rt は `response_format: {"type":"regex","regex": …}` を XGrammar の regex として受ける (`native_v41.rs:238-242`、`native_v41/constraints.rs:26-29`)。思考モードでは `</think>` の後だけに効く。
- `tools/zh_regex.py` が、2,278 字を 1,007 区間にまとめた否定の文字クラスを作る (`work/zh/serve/answer_regex.txt`、4,260 バイト)。
  - 文字単位の判定なので、バイト片の連結で簡体字を作る経路も塞ぐ。
- **ツール付きの要求には使えない。** `or[regex, ツール呼び出し]` になり、「文章を書いてからツールを呼ぶ」形が書けなくなる (`native_v41/constraints.rs:33-37`)。ツールの無い日本語評価 (ELYZA-tasks-100、Japanese MT-Bench、MGSM ja、M-IFEval-Ja) で、マスクの有無の A/B を取るために使う。
- 確かめること: 1 回目の要求で XGrammar の文法コンパイルにかかる時間 (以後は 64 件の LRU に入る)、`fill_bitmask` の 1 行あたりの時間、エラーにならないこと。

## 5. 抑制の方式と誤抑制の扱い

### 5.1 方式の比較 (課題の (a)〜(c))

| 方式 | 評価 | 理由 |
|---|---|---|
| (a) 回答部分だけ Z1 を -inf | **採用** | 日本語コーパスでの誤抑制は 21 / 409 万トークン (中国地名の引用だけ)。混入しかける位置では、日本語の字体が top-1 にある (§1.2)。簡体字の文の 97% を 2〜3 トークン目で止める |
| (a') 大きな負の bias (例 −5) | 不採用 | ds41rt のサンプラーには加算 bias の段が無く、全カーネルの改修が要る (§3.1)。-inf で困る例 (正当な Z1) は引用だけで、それは (b) で外せる。柔らかくすると、v0 の 2% の 约 が 0.01% 残る程度の差で、利点が無い |
| (a'') T2 (中国語の語) も禁止 | **不採用** | GLM の日本語回答の 2.2% が正当に T2 を使う (列入 = 配列入力、不均一、的主張、不等式)。BPE の切れ目に依存するので、語のリストでは判定できない |
| (a''') 思考の部分も禁止 | 不採用 (選べるようにはする) | 思考の Z1 の質量は回答の 40 倍ある。思考の分布を変えると推論の質に響きうる。思考は利用者に見せる本文ではない |
| (b) 言語判定で有効化 | **採用** (`auto`) | 判定は最新のユーザー発話で行う。文脈全体で判定すると 5.3% の要求で抑制が外れる (§1.3) |
| (c) 簡体字→日本語の字の後処理 | **不可** | 理由は 4 つある。(1) 生成済みのトークンが KV と文脈に残り、以後の生成が中国語寄りの状態から続く。(2) 置換は 1 対多 (发 → 発 / 髪) で、正しい語を選べない。(3) 次のターンで、クライアントが返す置換後の文字列が出力のトークン列と一致しない。ds41rt の token radix の接頭辞キャッシュが外れ、再 prefill になる。(4) ストリーミングでは、出した後の差し替えができない。マスクなら、モデル自身が次点 (ほぼ常に日本語の同じ語) を選ぶ |

### 5.2 誤抑制の場面と扱い

| 場面 | 扱い | 根拠 |
|---|---|---|
| 中国の人名・地名・企業名 (習近平、華為) | マスクのままでよい。日本語の文では日本の字体で書くのが慣例で、マスクはそちらに寄せる | §1.2 の top-1 はいずれも日本の字体 |
| 中国語の引用・中国語の学習 (「谢谢」と言う) | ユーザー発話に中国語を求める語か簡体字があれば `auto` で off | §3.3 |
| ユーザーが中国語で質問、中国語訳を依頼 | off | 同上。GLM のトラフィックでは利用者の発話が中国語だったのは 11 件 (r3_japanese §2.2) |
| ツール引数 (ファイルの書き込み、検索語) | DSML 内は解除 | 実トラフィックの回答の Z1 のうち 26 個 (4%) がツール呼び出し内だった |
| コードフェンス内の中国語の文字列 | 文脈の Z1 が 20 個以上 (要求の 0.6%) なら解除、それ以外は禁止 | 12 個 (2%) がフェンス内だった |
| 繁体字・日本の旧字体 | 対象外 (誤抑制しない) | Z1 は GB2312 の簡体字で JIS に無い字だけ |
| 稀な簡体字 (バイト片で表す 1,072 字) | 漏れる (出現数で約 1%) | §1.1。気になる場合は §3.6 の文字単位の regex、または段階 1 の拡張 (直前のトークンが不完全な UTF-8 で終わる行だけ、完成させると簡体字になる続きを禁じる表、約 60 行) |
| 明示の上書き | 要求ごとに `ds41rt_lang_guard: "off"`。サーバー全体は `--lang-guard off` | §3.3 |
| ds41rt のリリース評価の "Multilingual" (繁体字中国語) | 発話が中国語なので `auto` で off。繁体字は元から対象外 | `scripts/release_semantic_quality.py:165-176` (r3_japanese §1.3) |

| 項目 | ds41rt 段階 1 | ds41rt 段階 2 | vLLM (structured outputs) |
